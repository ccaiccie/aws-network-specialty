VPC Route Server BGP and BFD driven route-table convergence for virtual-appliance failover

Primary feature lesson sourceDynamic routing in your VPC using VPC Route Serverhttps://docs.aws.amazon.com/vpc/latest/userguide/dynamic-routing-route-server.html

Classification/platform: Official AWS VPC feature architecture documentation. Source date: no update date displayed; checked 2026-09-13. Supports: Route Server scope, supported route tables, BGP/BFD route learning, RIB/FIB selection, IPv4/IPv6 behavior, and service limits.

Scenario support sourceHow Amazon VPC Route Server workshttps://docs.aws.amazon.com/vpc/latest/userguide/route-server-how-it-works.html

Classification/platform: Official AWS feature-behavior and failover example. Source date: no update date displayed; checked 2026-09-13. Supports: The device-failure sequence, BFD detection, route withdrawal, MED preference, and route-table next-hop replacement.

Essence / mental model

VPC Route Server brings dynamic routing into a VPC route-table domain. Route Server endpoints form BGP sessions with network appliances through route-server peers; BFD can detect a failed peer rapidly. Learned routes enter a routing information base, best-path processing builds a forwarding information base, and the service writes the selected next hops into associated VPC or internet-gateway route tables. The result is controlled route convergence without a custom Lambda function editing routes. It supports IPv4 and IPv6 and is intended for traffic between VPC workloads and virtual network functions. It does not program Transit Gateway route tables or route tables associated with a virtual private gateway. Those boundaries prevent the feature from being mistaken for a universal BGP controller.

Architecture, dependencies, and normal flow

Place Route Server endpoints and redundant appliances in separate Availability Zones, and associate only the route tables that the service should program. Give the AWS side and peers deliberate private ASNs. Devices advertise prefixes and attributes such as MED; the best route identifies an appliance ENI as the VPC route-table target. Decide whether learned routes should persist when every BGP session is down. Persisting can avoid abrupt withdrawal during maintenance, but can also retain an unusable next hop; disabling persistence favors correctness when liveness is authoritative. Configure BFD consistently on both sides, avoid overlapping advertisements, and preserve a management path that does not depend on the appliance route being repaired. Internet-gateway route tables and subnet route tables solve different ingress and east-west patterns, so bind each route server to an explicit traffic contract.

Production scenario: symptom, competing hypotheses, and decision

Two EC2 firewalls advertise 192.0.2.0/24. Device A uses the lower MED and carries production traffic; Device B is standby. After Device A loses its data-plane interface, its BGP session remains established because BFD was not configured on the device, so the Route Server continues to install A's ENI as the next hop. The subnet route looks valid while probes fail. Competing hypotheses include security-group filtering, application failure, stale BGP reachability, and a missing route-table association. Operators compare BFD state, peer logs, the Route Server RIB/FIB, and the actual route target. They enable matched BFD settings, verify the route withdraws, and observe Device B become the selected next hop. The rollback is to disable the new peer setting, not to hand-edit every route table.

Essence / mental model

Direct Connect BGP route visibility exposes what AWS accepted from a customer router and what AWS advertised to that router on a virtual interface. Accepted routes are post-inbound-policy routes retained by AWS; advertised routes are the prefixes AWS sends toward the customer. Every entry can include prefix, address family, AS path, supported community values, and the timestamp from which route age is derived. This is more precise than treating an established BGP session or a route on the customer router as proof of exchange. The console shows separate Accepted routes and Advertised routes tabs, while ListVirtualInterfaceRoutes supports automation and filters. Internal or unsupported communities are not exposed, so absence from this view is not evidence that no internal attribute exists.

Architecture, dependencies, and normal flow

Use the feature as a route-contract check for each private, transit, or public VIF. Define which prefixes should arrive at AWS, which AWS prefixes should return, their address families, expected AS paths, and permitted Direct Connect communities. Query accepted and advertised directions independently. A route that the router claims to advertise but that is absent from Accepted routes was filtered, exceeded a boundary, or never reached the session; a route in Accepted routes but missing from a downstream VPC or Transit Gateway requires analysis after the VIF. Route age is operationally valuable during changes because a recent timestamp can identify a withdrawal and relearn, yet age alone does not say why. Collect snapshots before and after a maintenance event rather than relying on screenshots taken after convergence.

Essence / mental model

A Transit Gateway network-function attachment connects AWS Network Firewall directly to a transit gateway. AWS provisions the routing components behind the attachment, so the design does not require a customer-managed inspection VPC with per-AZ firewall endpoint routes. In the Transit Gateway console the object appears as a Network function attachment, while Network Firewall owns the firewall and policy. Route tables still decide which source attachments send traffic to the firewall and where inspected traffic goes next. Direct attachment simplifies infrastructure, but it does not create inspection intent automatically. In cross-account use, the Transit Gateway owner and firewall owner are separate roles, and the attachment can remain pending until the required share and acceptance steps are complete.

Architecture, dependencies, and normal flow

Start with traffic domains: source spokes, protected destinations, and the return path. Create the firewall through Network Firewall using the Transit Gateway, then associate and propagate the network-function attachment into route tables that express before-inspection and after-inspection paths. Avoid broad defaults until a canary flow proves symmetry. For separate accounts, the Transit Gateway owner shares the gateway through AWS RAM, the firewall owner accepts the share and creates the firewall, and the Transit Gateway owner accepts the resulting attachment unless auto-accept is enabled. A READY firewall and an AVAILABLE attachment are prerequisites, not proof that Transit Gateway route tables steer traffic through it. Document which account can update firewall policy and which controls the routes.

Essence / mental model

Route 53 Global Resolver is a global anycast recursive DNS service for workloads, branches, and remote users that need centralized DNS resolution and security outside a single VPC. Clients can use classic DNS on port 53, DNS over TLS on 853, or DNS over HTTPS on 443. Access sources and their rules identify which client CIDRs can query and which protocols they may use. DNS filtering, split-horizon behavior, and encrypted transport are separate choices. For DoH and DoT, EDNS Client Subnet can preserve useful client-network context for downstream authoritative decisions, but it deliberately shares part of the client prefix and must be governed as data. Global Resolver is distinct from Route 53 Resolver inbound and outbound endpoints inside VPCs.

Architecture, dependencies, and normal flow

Choose access locations close to users, publish the intended protocol endpoint, and make access-source CIDRs narrow enough to express real networks. Prefer encrypted DoH or DoT for untrusted access paths; keep Do53 only where legacy devices require it and the transport is controlled. Build split-horizon policies so internal names receive private answers while public names remain correct for external clients. Add domain filtering and logging without creating a circular forwarder chain. Decide whether EDNS Client Subnet is necessary for localization and, if so, limit the prefix precision shared. High availability requires client configuration with the provided resilient endpoint behavior and independent network paths; a single branch firewall that blocks port 443 can defeat an otherwise global service.
