IPv6 egress-only internet gateways: stateful outbound initiation, dual-stack routes, and policy boundaries

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-08. Source date: no update date displayed; checked 2026-09-08. Supports: The create, route association, command-line, and deletion workflow, including blackhole routes after gateway deletion.

Essence / mental model

An egress-only internet gateway is a horizontally scaled, redundant VPC component for IPv6. It lets a workload with a globally unique IPv6 address initiate communication to the internet or public AWS endpoints and permits the response, while preventing an internet host from initiating a new IPv6 connection through that gateway. The stateful initiation boundary is the essential mental model. It is not an IPv6 NAT device and it does not translate the workload address. A subnet uses it only when the associated route table selects the gateway—commonly with an IPv6 default route of ::/0. IPv4 remains a separate data plane: a dual-stack workload still needs an IPv4 route through a NAT gateway or another approved path if it must initiate IPv4 internet traffic.

Architecture, dependencies, and normal flow

Design the IPv6 and IPv4 paths independently. A dual-stack private subnet might route ::/0 to an egress-only internet gateway and 0.0.0.0/0 to a same-AZ NAT gateway, while more-specific routes keep AWS service, hybrid, or inspection traffic on private paths. Longest-prefix route selection still applies before the gateway behavior matters. You cannot associate a security group with the egress-only gateway itself; workload security groups and subnet network ACLs remain the enforcement points. Security groups are stateful, whereas NACLs require explicit return-port rules. The gateway admits responses only for flows initiated from the VPC, but application listeners can still be exposed through some other route or service, so the architecture must inventory every ingress path rather than treating the gateway as a universal firewall.

Essence / mental model

Direct Connect SiteLink lets supported private or transit virtual interfaces exchange traffic between Direct Connect points of presence in the same AWS partition over the shortest available AWS network path, without forcing that on-premises-to-on-premises traffic through an AWS Region. SiteLink is enabled per eligible VIF. A transit VIF attaches to a Direct Connect gateway and can participate; several private-VIF attachment combinations are supported, but public VIFs and a private VIF attached directly to a virtual private gateway are not. SiteLink does not work when an on-premises router advertises the same route to AWS on multiple VIFs, so prefix uniqueness is an architectural requirement rather than a cosmetic BGP preference. It is unavailable in the China and AWS GovCloud partitions and has separate pricing.

Architecture, dependencies, and normal flow

Treat SiteLink as a managed WAN path between locations, not as proof of end-to-end diversity. Each office still needs resilient local loops, customer routers, Direct Connect connections or LAGs, and a routing policy that avoids ambiguous duplicate advertisements. Decide whether the route is intended for SiteLink, a Region, or both, then model AWS path selection and customer-side BGP. When SiteLink is enabled, paths from AWS Regions can prefer a lower AS path from a Direct Connect location even when that location is associated with a different Region, so test traffic in both directions. MTU is also per VIF type: a private VIF can use 9001, while a transit VIF is limited to 8500. If two paths advertise the same prefix with different MTUs, effective behavior can fall back to 1500 and expose hidden fragmentation assumptions.

Essence / mental model

Cloud WAN service insertion steers traffic through network or security functions by expressing the intent in the core network policy. The design first creates a network function group, then places an inspection VPC or other supported attachment into it with an attachment policy, and finally applies segment actions. A send-via action is for bidirectional east-west flows between segments and inserts the function group between the two sides; it does not need a mirrored action in the reverse direction. A send-to action is for north-south traffic sent from a segment to a network function group, such as centralized egress. These policy objects generate the service routes, but they do not configure the firewall's own endpoints, policies, subnet routes, or acceptance state.

Architecture, dependencies, and normal flow

Define trust segments, inspection placement, and attachment ownership before writing actions. A production and development segment can be isolated from direct attachment-to-attachment communication while a send-via action permits only the intended inspected relationship. Network function groups are separate from normal segments and can require attachment acceptance. In a multi-Region core network, Cloud WAN can choose an inspection attachment in one of the Regions involved; Region priority and a single fallback Region can be specified. That selection must match stateful appliance symmetry, capacity, data-residency, latency, and failure objectives. Service insertion simplifies route automation, but a policy that points to an empty or unaccepted function group cannot create a healthy appliance path. Model both forward and return routes plus behavior when an inspection Region or attachment is unavailable.

Essence / mental model

Route 53 Resolver query logging records DNS queries and responses for associated VPCs, queries arriving through inbound Resolver endpoints, queries forwarded through outbound endpoints, and DNS Firewall evaluations. The record can identify account, Region, VPC, source address and resource, query name and type, response code, returned data, and firewall action. It is not a packet-by-packet census of every application lookup. Resolver caches answers for their TTL and logs only unique queries received for resolution; a later lookup served from cache can be absent even when the client succeeded. That cache blind spot makes silence ambiguous. Query logs are evidence about Resolver processing, not proof that a client used the returned address, established a connection, or received the same answer from its own stub or intermediate cache.

Architecture, dependencies, and normal flow

Create logging configurations in the account and Region that own the Resolver scope, choose CloudWatch Logs, S3, or Kinesis Data Firehose according to query and retention needs, and associate every intended VPC. Centralize with resource sharing or cross-account observability only after defining owners and privacy boundaries. For hybrid DNS, include inbound and outbound endpoints in the evidence model and correlate rules that decide which domain leaves the VPC. DNS Firewall actions can appear in the same record, which helps separate policy from upstream resolver failure. Design analytics for log-format version evolution: a minor version can add fields and a major version signals incompatible structure. Avoid availability alarms that treat one missing record as a failed lookup; use controlled cache-busting names or wait beyond TTL when testing the resolver path.

Essence / mental model

A network access control list is a subnet-level allow-and-deny control. Every subnet is associated with exactly one NACL at a time, while one NACL can protect multiple subnets. Inbound and outbound rules are separate and evaluated in ascending rule-number order; the first matching rule decides, and the terminal asterisk rule denies anything not matched. NACLs are stateless, so allowing an inbound TCP request does not automatically allow the outbound response. The return rule must match the client's ephemeral destination port, and the relevant range is chosen by the initiating client or managed service rather than by the server listener. Rules are evaluated when traffic crosses the subnet boundary, not for traffic routed between ENIs inside the same subnet.

Architecture, dependencies, and normal flow

Use NACLs as coarse, auditable subnet guardrails and explicit deny controls, not as a substitute for stateful security groups. Number rules in increments so urgent narrow denies can be inserted before broad allows. Model both directions for every initiated flow: a public client to TCP 443 needs inbound 443 and outbound ephemeral destination ports; an instance initiating a database connection needs outbound database port and inbound ephemeral return ports. Operating systems and AWS services use different ephemeral ranges—NAT Gateway, Elastic Load Balancing, and Lambda can require 1024–65535—so blindly copying a workstation range creates intermittent failures. Account for ICMP required by Path MTU Discovery. NACLs also cannot filter specific VPC-provided services such as Route 53 Resolver or instance metadata, which need their own controls.

Essence / mental model

An App Runner service uses public outbound access by default. Selecting Custom VPC associates a VPC Connector with the application so application-originated outbound connections use managed Hyperplane ENIs in the chosen subnets and the connector's security groups. The change does not move App Runner's public service ingress through those subnets. Incoming requests still use the service domain unless a separate private inbound design is configured. App Runner-managed traffic for source or image pulls, log delivery, and secret retrieval also remains on the service-managed path rather than the connector. This separation explains why a deployment can start and receive requests while its application cannot reach a database or a public API. Connector networking is outbound data-path configuration, not full placement of the App Runner runtime inside the VPC.

Architecture, dependencies, and normal flow

Select private subnets with routes to every downstream dependency and enough addresses for managed ENIs. The Hyperplane ENIs do not receive public IP addresses, so placing the connector in a subnet named or routed as public does not grant internet egress. A public IPv4 API requires a private-subnet route to a NAT gateway, while AWS services may be reached through approved VPC endpoints. Private databases need local, peering, Transit Gateway, or hybrid routes and destination security groups that allow the connector security group or correct CIDR. The connector security group's outbound rules are only one half of the policy. Reuse connectors with the same subnet and security-group combination where appropriate; first use can add one-time startup latency while the managed networking is prepared. Design inbound privacy separately from outbound VPC access.

Normal-state check: the configured Workload networking control point, its dependency chain, and its return/response behavior must all agree. Treat an available control-plane object as evidence of configuration state—not proof that the workload data path, name resolution, target process, or authorization layer works.

Production scenario: symptom, competing hypotheses, and decision

An App Runner API connects successfully to RDS after a VPC Connector is added but begins timing out to a third-party HTTPS API. The deployment itself is healthy and logs continue, because managed App Runner traffic does not use the connector. The selected subnets lack a default route to NAT. The team adds an approved same-AZ NAT egress path and connector security-group TCP 443 rule, then tests from the application. In another case, RDS still fails while NAT works; the RDS security group allows the subnet CIDR but the policy standard requires the connector security group as source. The team corrects the destination ingress and verifies the database listener. Removing the connector would restore public egress but would also lose the intended private database path, so it is not a complete solution.
