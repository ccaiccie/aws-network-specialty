Wavelength carrier-gateway edge routing, Carrier IP NAT, and mobile access

Classification/platform: Official AWS Prescriptive Guidance deployment pattern. Source date: no update date displayed; checked 2026-09-12. Supports: A concrete Terraform deployment, Regional-to-Wavelength validation, carrier-gateway checks, and mobile/carrier troubleshooting.

Essence / mental model

A carrier gateway is the Wavelength-specific VPC edge for traffic between a Wavelength subnet and the communications service provider network. It is not an internet gateway, NAT gateway, or Transit Gateway. A Wavelength workload keeps a private IPv4 address in the VPC; when the carrier allocates and the operator associates a Carrier IP, the carrier gateway performs the translation needed for inbound mobile-carrier reachability and outbound carrier or internet access. The Wavelength subnet route table must point the intended destination, commonly 0.0.0.0/0, to the carrier gateway. Regional VPC resources can still communicate with the Wavelength subnet through the VPC local route. This separates low-latency carrier access from ordinary Regional or internet-egress paths and makes route ownership explicit.

Architecture, dependencies, and normal flow

Start with an opted-in Wavelength Zone, a VPC that spans the parent Region and that Zone, a subnet created in the Wavelength Zone, and sufficient free IPv4 space. Attach one carrier gateway to the VPC, associate its identifier with the Wavelength subnet route, and attach a Carrier IP to the workload elastic network interface when inbound carrier access is required. The route target controls which traffic enters the carrier edge; the Carrier IP controls public/carrier translation; security groups and network ACLs still control the permitted flow. Because the feature is IPv4-oriented, do not infer an IPv6 egress path or egress-only gateway behavior. Preserve a Regional management or test path so a mobile-access failure can be separated from instance health. Terraform can declare the VPC, subnet, gateway, route, EC2 instance, and address association, but provider success is not a data-path test.

Essence / mental model

Private IP Site-to-Site VPN over Direct Connect adds IPsec encryption to traffic that already traverses a Direct Connect private transport. The VPN tunnel outside addresses are private rather than public, and the underlay is a transit virtual interface connected through a Direct Connect gateway to a Transit Gateway. The Transit Gateway transport attachment provides the IP reachability used to establish the private VPN tunnels; a separate VPN attachment carries the encrypted overlay and the workload prefixes. This distinction is essential: a healthy Direct Connect BGP session proves the transport can exchange routes, while an UP IPsec/BGP overlay proves a different layer. The design avoids public VPN endpoints while retaining dynamic routing and can support greater route scale than the ordinary public-IP VPN quotas documented for the service.

Architecture, dependencies, and normal flow

Build the underlay before the overlay. Assign a Transit Gateway CIDR that does not overlap connected networks; create and accept the Direct Connect gateway association; create the transit VIF; and confirm the resulting Connect-style transport attachment is available. The customer gateway IP should be a stable private loopback or LAN address reachable across the underlay, not the point-to-point BGP addresses of the transit VIF. When creating the VPN, select PrivateIpv4 for the outside address type and the transport attachment, then configure both tunnels and BGP sessions on the customer device. Private tunnel-inside and outside ranges may use documented RFC 1918 or shared space, but every address must remain unambiguous in the transport domain. Propagate or enter workload routes into the intended Transit Gateway route tables; transport reachability alone never installs application prefixes in the overlay route domain.

Essence / mental model

Cloud WAN can interconnect an existing Transit Gateway routing domain with a Cloud WAN segment through a peering between a core network edge and the Transit Gateway. The peer must be in the same Region, and the core edge and Transit Gateway require unique BGP ASNs. Unlike a static Transit Gateway peering design, this integration uses dynamic BGP route exchange. The peering establishes adjacency, but it does not by itself choose a Transit Gateway route table or a Cloud WAN segment. A route-table attachment maps one Transit Gateway route table to the peering and, through the core network policy table, to a specific Cloud WAN segment. Treat peering state, attachment state, policy execution, and learned routes as four distinct control points.

Architecture, dependencies, and normal flow

Use the integration when a brownfield Transit Gateway domain must participate in a policy-managed Cloud WAN without migrating every attachment at once. Verify ASN uniqueness and same-Region placement first, then create the peering, accept or complete its cross-account workflow, and wait for availability. Create the route-table attachment for exactly the Transit Gateway route table that represents the intended domain. Update the Cloud WAN core network policy so the attachment maps to the correct segment and deploy the policy version. Static routes cannot replace the BGP behavior of this peering. Plan route summarization and overlap handling before joining domains: a segment boundary is useful only when attachment policies and allowed route exchange express the intended isolation. A second route-table attachment may be required for a separate Transit Gateway domain rather than combining unrelated consumers.

Classification/platform: Official AWS configuration procedure. Source date: no update date displayed; checked 2026-09-12. Supports: CIDR-location creation, IPv4/IPv6 prefix-length limits, block management, and record association workflow.

Essence / mental model

Route 53 IP-based routing selects a record according to the DNS resolver source IP mapped into a CIDR collection. A collection contains named locations, and each location contains IPv4 or IPv6 blocks. For records with the same name and type, Route 53 chooses the location whose block most specifically matches the observed source address; a wildcard location can provide the fallback. This is DNS-answer steering, not packet routing or geolocation. The source visible to authoritative DNS is normally a recursive resolver, or an EDNS Client Subnet value when supported, so client placement must be validated empirically. The policy is available for public hosted zones, not private hosted zones, and the same record family must consistently reference the same CIDR collection.

Architecture, dependencies, and normal flow

Use IP-based routing when contractual ISP ranges, resolver ranges, or known client networks require deterministic answers that geography or latency policies cannot express. Create the CIDR collection in the correct account, add locations, then add nonoverlapping or intentionally nested blocks. Route 53 supports IPv4 blocks from /1 through /24 and IPv6 blocks from /1 through /48; more-specific client addresses can still match a stored block through longest-prefix selection. Build a wildcard location for unknown resolvers unless NXDOMAIN or absence is intentional. For a given DNS name and type, keep every IP-based record tied to one collection. Model resolver behavior: a mobile device may use a carrier recursive resolver outside the handset prefix, and ECS truncation may change the match. TTL determines how quickly a changed mapping is observed by cached clients.

Essence / mental model

Amazon MSK multi-VPC private connectivity gives Kafka clients in other VPCs and accounts a managed AWS PrivateLink path to a provisioned MSK cluster in the same Region. It avoids VPC peering and Transit Gateway routing and supports overlapping client and cluster CIDRs because clients connect to service-managed endpoint addresses rather than directly routing into the broker VPC. The cluster owner enables multi-VPC connectivity for supported authentication schemes and attaches a cluster policy that authorizes cross-account actions. Each client owner then creates a managed VPC connection in its own VPC with matching Availability Zone placement. Network connectivity and Kafka authorization remain distinct: IAM, TLS, or SASL/SCRAM establishes supported authentication, while cluster policy and Kafka permissions control actions. Anonymous authentication is not supported for this feature.

Architecture, dependencies, and normal flow

Confirm the cluster is provisioned, ACTIVE, runs Apache Kafka 2.7.1 or later, and does not use the unsupported kafka.t3.small broker type. Choose IAM, TLS mutual authentication, or SASL/SCRAM as supported by the workload, then enable the corresponding PrivateLink connectivity on the cluster and wait for the update. Add a cluster resource policy that grants the client account the minimum actions required to create and use a VPC connection. The client creates a managed VPC connection using subnets whose Availability Zone IDs match the cluster and whose count matches the cluster subnet count, plus a security group that permits broker traffic. Region names can vary between accounts, so compare AZ IDs. Retrieve the connection-specific bootstrap brokers; do not reuse ordinary cluster endpoints by assumption.
