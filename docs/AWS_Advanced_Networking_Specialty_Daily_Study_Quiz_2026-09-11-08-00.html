IPAM pool hierarchy and organization-wide VPC allocation enforcement with service control policies

Primary feature lesson sourceHow IPAM works - Amazon Virtual Private Cloudhttps://docs.aws.amazon.com/vpc/latest/ipam/how-it-works-ipam.html

Essence / mental model

Amazon VPC IP Address Manager turns address planning into a governed allocation hierarchy. A scope is the top-level isolation boundary for one logical network. Every IPAM begins with public and private scopes; separate private scopes can represent disconnected networks that intentionally reuse RFC 1918 space. Pools divide a scope into contiguous CIDRs according to routing and security intent, and child pools can subdivide a global allocation into Regional, environment, business-unit, or workload ranges. An allocation is the actual CIDR assignment to another pool or an AWS resource such as a VPC. The important mental model is that IPAM owns the allocation decision, while the VPC, subnet, route table, and security controls own reachability. A VPC created from an IPAM pool receives a nonoverlapping range according to the pool hierarchy and allocation rules; it does not automatically receive subnets, routes, internet access, or trust.

Architecture, dependencies, and normal flow

Start at failure domains and aggregation boundaries. Reserve a top-level private range, create Regional child pools with the correct locale, then subdivide into production, nonproduction, and platform pools sized for growth rather than only current consumption. Keep connected networks inside a scope where overlaps can be detected; use a distinct scope only when address reuse is deliberate and those networks will remain isolated or traverse translation. Pool allocation rules can constrain eligible netmask lengths and other criteria, but the surrounding organization design still matters: decide which account administers IPAM, which accounts consume shared pools, and which route-domain summaries the hierarchy must support. IPv4 and IPv6 planning should be explicit, because a governance rule that checks only an IPv4 pool identifier does not prove that IPv6 allocations follow the same policy. An SCP is a permission guardrail, not the allocator; it denies disallowed API shapes while IPAM performs the allocation.

Essence / mental model

AWS VPN CloudHub is a virtual-private-gateway design for securely relaying traffic between multiple customer sites, not only between a site and a VPC. Each site has a customer gateway and a dynamically routed Site-to-Site VPN connection to the same virtual private gateway. Each customer gateway uses a unique BGP ASN and advertises its site-specific, nonoverlapping prefixes. The virtual private gateway receives those routes and re-advertises them to the other BGP peers, producing hub-and-spoke reachability over IPsec. The VPC is optional for site-to-site relay, though workloads can also participate when VPC route tables propagate or contain the necessary routes. A Direct Connect connection associated with the virtual private gateway can participate as another path for a headquarters site. CloudHub is intentionally simple; it is not a Transit Gateway route-table segmentation fabric and it does not make overlapping branches interoperable.

Architecture, dependencies, and normal flow

Inventory every branch prefix and ASN before creating the hub. Use specific advertisements between customer gateways and the virtual private gateway, and use deliberate aggregates in VPC route tables only when the aggregate cannot hide an overlapping or unreachable component. Configure both IPsec tunnels for every VPN connection; one connection containing two tunnels protects against AWS tunnel maintenance, while a second customer gateway device and second VPN connection protect against an on-premises device failure. Those are different failure domains. Decide how BGP attributes on the customer devices choose a primary path when a branch also has Direct Connect or two appliances, and test what is re-advertised after withdrawal. CloudHub traffic incurs ordinary VPN connection and outbound transfer charges, so compare it with Transit Gateway or SD-WAN designs when segmentation, scale, or deterministic multi-table routing is required.

Essence / mental model

A Transit Gateway prefix-list reference is route indirection. Instead of entering the same destination CIDRs into multiple Transit Gateway route tables, an operator references a managed prefix list and selects either an attachment for forwarding or Blackhole for dropping. Every CIDR entry in the list appears as a route in the Transit Gateway route table. The prefix list remains a separate regional object with its own entries and versions; the reference supplies the Transit Gateway forwarding disposition. You cannot edit the generated individual routes on the route table's Routes tab. Change membership at the managed prefix list, or change the reference when traffic should use a different attachment or become blackholed. This separation reduces repetitive edits but increases blast radius: one prefix-list update can alter many effective routes at once.

Architecture, dependencies, and normal flow

Use a list for a coherent destination class whose members should share the same Transit Gateway next hop, such as approved partner networks, inspection destinations, or a quarantine set. Do not mix prefixes that require different failure handling merely to reduce route count. Define an owner, maximum entries, address family, Region, and consumer route tables. Model interactions with static and propagated routes before deployment, especially for overlapping destinations and more-specific paths. An Active reference needs an attachment that is available and whose downstream route domain knows the destinations. A Blackhole reference is a policy result, not evidence that every alternative path is blocked; verify route selection for each relevant prefix. When changing attachments, map both forward and return directions so a stateful appliance or destination does not see asymmetric sessions.

Essence / mental model

AWS Cloud Map is a service registry whose namespace, service, and instance objects turn changing application endpoints into discoverable names or API results. A service is a template inside a namespace. It defines the service name, optional Route 53 DNS configuration, and health behavior; registered instances contribute address, port, and custom attributes. A client locates instances with DNS when the namespace supports DNS queries, or with DiscoverInstances for API-based discovery. This is not a load balancer: DNS answers and cached records direct clients toward instances, while connection retries, application protocol, and instance behavior remain the client's responsibility. Service-level attributes can carry operational hints such as endpoint weights or retry preferences for API consumers, but Route 53 DNS routing follows the service's configured routing policy and record type.

Architecture, dependencies, and normal flow

Choose the namespace type and name according to the clients and authority boundary. A private DNS namespace associates with a VPC and provides names through Route 53 private DNS; an HTTP namespace supports API discovery without creating DNS records. Inside a DNS-capable namespace, choose Weighted when Route 53 should return one randomly selected instance with equal record weights, or Multivalue Answer when it should return up to eight healthy values. The labels are easy to misread: Cloud Map's weighted policy does not let each registered instance receive an arbitrary DNS weight. If no instances are healthy, Route 53 can respond as though all instances were healthy, so clients still need failure handling. Select A, AAAA, both, CNAME, or SRV based on what registration data exists and what the client resolver understands.

Essence / mental model

Elastic Fabric Adapter is an EC2 network interface for latency-sensitive AI, machine learning, and high-performance computing. Its EFA device exposes OS-bypass and congestion-control capabilities through the Scalable Reliable Datagram transport, allowing supported libraries to communicate without sending every message through the kernel TCP/IP stack. Libfabric is the user-space interface integrated by Open MPI, Intel MPI, NCCL, and NIXL. A traditional EFA interface includes both EFA and ENA functions so the instance has ordinary IP networking as well as fabric communication; an EFA-only interface exposes only the EFA device and is designed for specialized multi-interface topologies. EFA improves inter-instance communication, but it cannot compensate for an unsupported instance type, wrong Availability Zone, missing library provider, security-group block, or a workload that still selects TCP.
