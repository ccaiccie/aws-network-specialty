DHCP option sets, DNS delivery, and VPC-level network configuration

Essence / mental model

A DHCP option set is a VPC-level bundle of settings delivered to instances when they obtain or renew an address. It is not a subnet object and it does not replace the DHCP service built into the VPC. One VPC is associated with one option set at a time, so the design decision is deliberately broad: decide whether the VPC should use AmazonProvidedDNS, a domain-name suffix, custom DNS servers, or a mix appropriate for a hybrid resolver strategy before attaching workloads. Treat the option set as part of the VPC contract, alongside CIDR ranges, route tables, and DNS attributes.

Architecture, dependencies, and normal flow

The practical design tension is between keeping AWS-native name resolution working and delivering enterprise DNS behavior. For a VPC that must resolve private AWS names as well as corporate names, use Route 53 Resolver endpoints and forwarding rules for the conditional domains; do not point every workload at an on-premises DNS server without verifying the return path and the resolver behavior. DHCP option sets are immutable after creation, so a controlled change creates a new set and then associates it with the VPC. That makes a rollback explicit: retain the prior set, validate from representative subnets, and switch back if authoritative-name or search-domain behavior is wrong.

Normal-state check: the configured VPC foundations control point, its dependency chain, and its return/response behavior must all agree. Production scenario: symptom, competing hypotheses, and decision

A platform team changes the domain-name-servers value so Linux instances receive corporate DNS addresses. New instances can resolve internal names, but they no longer resolve an AWS private hosted zone consistently. Diagnose the configuration as a DNS architecture issue, not a security-group issue: inspect the option set associated with the VPC, test the resolver path from an instance, verify Route 53 Resolver forwarding for only the corporate suffixes, and confirm the enterprise resolvers can reach the required AWS resolver path. The safe corrective action is to deploy an option set that preserves the intended VPC DNS behavior and uses conditional forwarding rather than a blanket replacement.

Essence / mental model

An AWS Site-to-Site VPN connection is built from two independent IPsec tunnels. The customer gateway device must be configured to negotiate the tunnel options AWS supports, including IKE versions, encryption and integrity algorithms, Diffie-Hellman groups, and Dead Peer Detection behavior. Advanced design starts with the assumption that a tunnel can fail or be replaced while the connection remains a service: use both tunnels, keep routing state meaningful, and verify the on-premises device fails traffic over instead of pinning it to a single stale security association.

Architecture, dependencies, and normal flow

Choose tunnel options that align with the customer gateway’s supported cryptographic profile and the organization’s policy, then document the actual negotiated parameters. If BGP is available, it supplies route exchange and can withdraw a failed path more predictably than static routes. Static routing can still be viable, but it makes liveness and failover design more operationally sensitive. Avoid designing around a single tunnel because maintenance and endpoint replacement are normal events. For sensitive hybrid routes, make route preference intentional: Direct Connect, VPN, transit gateway, and virtual private gateway each have different placement and failover implications.

Essence / mental model

A Transit Gateway peering attachment connects two transit gateways, including gateways in different AWS Regions. The attachment itself is not a complete route: each side needs deliberate route-table entries for the CIDRs that should traverse the peer. That separation is a feature. It lets network owners decide which attachments may reach which remote prefixes and makes accidental transitive connectivity less likely. An advanced design models the topology as two independently governed routing domains joined by an attachment, not as a magic global mesh.

Architecture, dependencies, and normal flow

Before creating a peer, inventory the non-overlapping IPv4 and IPv6 CIDRs, ownership boundaries, inspection insertion points, and failure domain. Decide whether the route is static, propagated from another attachment, or summarized. For cross-Region designs, locate stateful inspection with return-path symmetry in mind and avoid propagation that allows spokes to use each other as unintended transit. A peer can support a backbone pattern, but a simple hub-and-spoke route table association and propagation model is often easier to audit than broad default routes.

Essence / mental model

Route 53 Resolver outbound endpoints let workloads in a VPC forward DNS queries for selected domains to resolvers on a connected network. The endpoint exposes private IP addresses in chosen subnets, and Resolver rules decide which suffixes should use those endpoints. The basic pattern is split-horizon DNS: AWS-native names stay with the VPC resolver while a corporate suffix is sent over VPN or Direct Connect to an authoritative enterprise resolver. The route, security policy, and DNS rule must all agree; a rule without a network path is not a resolver architecture.

Architecture, dependencies, and normal flow

Place outbound endpoint ENIs in resilient subnets across Availability Zones and permit the required DNS traffic to the target resolvers. Keep forwarding rules narrow and authority-oriented—forward corp.example only when that network is authoritative for it. A broad catch-all rule can unintentionally bypass expected AWS resolution or create ambiguous recursion. Build the reciprocal on-premises design carefully: conditional forwarding back to AWS belongs only for AWS-private zones that the VPC resolver owns. Document the desired owner for each namespace before configuring either side.
