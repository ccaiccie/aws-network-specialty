Bring Your Own IP address lifecycle with RDAP or IPAM proof, ROA authorization, Regional pools, and network border groups

Primary feature lesson sourceBring your own IP addresses (BYOIP) to Amazon EC2https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-byoip.html

Scenario support sourceTutorial: Bring your IP addresses to IPAMhttps://docs.aws.amazon.com/vpc/latest/ipam/tutorials-byoip-ipam.html

Classification/platform: Official Amazon VPC IPAM implementation tutorial. Source date: no update date displayed; checked 2026-09-17. Supports: DNS TXT verification, organization sharing through IPAM, one-time onboarding with distribution across Regions, and route-protection monitoring options.

Essence / mental model

BYOIP separates ownership of an address range from operation of that range in AWS. The organization continues to own the public IPv4 or IPv6 space, proves control to AWS, provisions the CIDR into an address pool, advertises it through AWS, and allocates addresses to supported resources. AWS accepts either an RDAP-based X.509 control proof for registries that support RDAP or a DNS TXT validation workflow through VPC IPAM. Publicly advertised space also depends on an appropriate Route Origin Authorization so Internet routing can validate the AWS origin. These are distinct gates: a clean registry record is not the advertisement itself, and a provisioned pool is not yet globally reachable.

Architecture, dependencies, and normal flow

Start with the registry and routing contract. The narrowest public IPv4 prefix supported is /24; public IPv6 is /48, while a non-publicly advertisable IPv6 block can be as specific as /60. Each range is brought to one AWS Region at a time in the EC2 workflow, with five ranges per Region by default, although support can review quota increases. IPAM is the stronger organization-scale model because it can onboard address space once and distribute it across Regions and accounts through Organizations. For a Local Zone, select the network border group deliberately: AWS advertises from that group, and an Elastic IP and the resource using it must reside in the same group. Design rollback before advertising, because withdrawal and re-advertisement affect public reachability and reputation.

Classification/platform: Official AWS Direct Connect architecture overview. Source date: no update date displayed; checked 2026-09-17. Supports: The operational and ownership distinction between a customer-requested dedicated connection and a partner-provisioned hosted connection.

Essence / mental model

A hosted Direct Connect connection is a logical connection that an AWS Direct Connect Partner provisions for a customer on a partner-managed physical connection. The customer cannot request it directly in the Direct Connect console; after the partner creates it, the customer must accept it before use and then create virtual interfaces. This ownership boundary changes escalation, capacity planning, and change control. AWS supports hosted speeds from 50 Mbps through 25 Gbps where the partner and location qualify. The configured rate is a hard service boundary because AWS polices the traffic: excess traffic is dropped rather than buffered into an unlimited burst entitlement.

Architecture, dependencies, and normal flow

Choose hosted versus dedicated based on operational ownership as well as bandwidth. A dedicated connection is a physical Ethernet connection associated with one customer and can be requested through AWS interfaces. A hosted connection is provisioned on the customer's behalf, and only the partner can change its port speed. Confirm that the partner supports an in-place upgrade or downgrade and that the location supports the requested rate; 25 Gbps hosted connections require a location with 100 Gbps ports. Treat MTU as a parent-child dependency: jumbo frames can be enabled on the hosted connection only if the hosted parent connection originally enabled them. The customer virtual interface, router MTU, VLAN, BGP, and downstream path must agree.

Transit Gateway VPN attachment route safety, dynamic-routing ECMP, and MTU or PMTUD boundaries

Classification/platform: Official Amazon VPC Transit Gateway limits and behavior reference. Source date: no update date displayed; checked 2026-09-17. Supports: ECMP eligibility, attachment bandwidth context, 8500-byte non-VPN versus 1500-byte VPN MTU, MSS clamping, and interfaces on which Transit Gateway does or does not support PMTUD.

Essence / mental model

A Site-to-Site VPN attached to Transit Gateway is both a hybrid tunnel set and a Transit Gateway route-table target. It supports IPv4 and IPv6 and can use dynamic BGP routes or declared static routes. Dynamic routing is the prerequisite for Transit Gateway to aggregate equal-cost VPN tunnels with ECMP; static VPNs cannot use ECMP. The route-table boundary is security-sensitive: AWS warns that a static Transit Gateway route targeting a VPN attachment is not filtered by the Site-to-Site VPN route declarations, so a broad static route can forward traffic that operators assumed BGP policy would constrain. Treat the attachment, route table, tunnel state, and customer-gateway route policy as separate controls.

Architecture, dependencies, and normal flow

For scalable bandwidth and convergence, prefer BGP where the customer gateway supports it, advertise only approved prefixes, and enable Transit Gateway VPN ECMP only when the paths are truly equal and the on-premises side can hash and return traffic symmetrically. A VPN path has a 1500-byte Transit Gateway MTU, while traffic among VPC, Direct Connect, Connect, and peering attachments can use an 8500-byte Transit Gateway MTU. Transit Gateway performs MSS clamping, but its PMTUD support is asymmetric by attachment type: it generates fragmentation-needed or packet-too-big feedback for traffic ingressing VPC and Connect attachments, not for Site-to-Site VPN, Direct Connect, or peering attachments. Design end-host MTU, ICMP policy, and packet-size tests accordingly.

Essence / mental model

Route 53 geolocation routing answers according to the estimated location from which the DNS query originates, not the confirmed physical location or identity of the end user. Route 53 maps the resolver address or available EDNS0 client-subnet information to a continent, country, or supported U.S. state. When configured geographic regions overlap, the smallest matching geography wins: a state can override its country, which can override its continent. Some addresses cannot be mapped, and some locations have no explicit record. A Default geolocation record is therefore a coverage control; without it, Route 53 returns no answer for unmapped or unconfigured locations.

Architecture, dependencies, and normal flow

Use the same name and record type for the entire geolocation record group, assign a unique record identifier to each member, and write the intended precedence as a table before deployment. Include records at the minimum granularity required for a business rule and create a Default response for everything else. In a private hosted zone, geography is closest to the AWS Region of the querying resolver, so do not infer an employee's residence from a private query result. If health checks are attached, use a TTL of 60 seconds or less so recursive caches respond promptly to health changes; during initial record changes, a short TTL such as 300 seconds also reduces rollback delay.

Essence / mental model

By default, the Amazon VPC CNI allocates Pod addresses from the node's primary subnet. Custom networking moves Pod address allocation to secondary ENIs created in subnets named by ENIConfig custom resources. Each ENIConfig supplies a subnet and one or more security groups for the Pods using it. The node's primary ENI remains in the primary VPC CIDR for host networking and node functions, while Pod secondary ENIs can use a secondary VPC CIDR such as RFC 6598 shared space. This relieves pressure on scarce primary RFC 1918 ranges, but it creates an explicit per-Availability-Zone mapping, distinct Pod policy, and a rollout boundary at node creation.

Architecture, dependencies, and normal flow

Associate a non-overlapping secondary IPv4 CIDR with the VPC, carve a Pod subnet in every node Availability Zone, and ensure all VPC, Transit Gateway, firewall, on-premises, and service routes understand that Pod range. AWS recommends considering 100.64.0.0/10 space because it is less likely to collide with corporate RFC 1918 allocations, but collision analysis remains mandatory. Set AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG=true and create ENIConfig resources whose names match Availability Zones, or annotate each node with the intended ENIConfig. The Pod security groups in ENIConfig are applied to secondary ENIs. Because the primary ENI no longer contributes Pod addresses, maximum Pods per node can decrease; prefix delegation can improve density and can be used with custom networking.

Security, governance, scale, and failure boundaries
