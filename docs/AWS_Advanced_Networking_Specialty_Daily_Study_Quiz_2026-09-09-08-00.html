VPC peering as pairwise private routing: nontransitivity, DNS options, MTU, and edge-to-edge limits

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-09. Source date: no update date displayed; checked 2026-09-09. Essence / mental model

A VPC peering connection is a one-to-one relationship between two VPCs. It lets routes in each VPC target the peer so workloads use private IPv4 or IPv6 addresses, including across accounts and Regions. AWS builds the connection from the VPC fabric rather than a customer gateway or appliance, so the construct has no separately sized bandwidth device or single gateway failure point. Inter-Region peering traffic stays on the AWS backbone and is encrypted before it leaves AWS facilities. Those properties do not make peering a routing protocol: the accepter must approve the request, each side must install the intended routes, security policy must permit the flow, and optional DNS-resolution behavior must be enabled deliberately. The decisive boundary is nontransitivity. If A peers with B and B peers with C, A cannot use B as transit to C. Peering also cannot provide edge-to-edge access to a peer's internet gateway, NAT gateway, Site-to-Site VPN, Direct Connect path, or gateway endpoint.

Architecture, dependencies, and normal flow

Use peering for a bounded pair of VPCs with nonoverlapping CIDRs and a small, explicit route exchange. As the number of VPCs grows, the full-mesh relationship grows approximately with n(n-1)/2 and route ownership becomes operationally brittle; Transit Gateway or Cloud WAN is normally the better hub when controlled transit is required. Plan both address families and both directions. A route in only one VPC creates asymmetric reachability, while an overly broad aggregate can expose subnets that were not intended to communicate. Same-Region peers can reference peer security groups, but that does not replace routes or target-side rules, and cross-Region control capabilities differ. DNS resolution over peering is an option on the connection: public DNS names can resolve to private addresses across the peer only when the documented setting and VPC DNS attributes align. Model MTU explicitly—same-Region peering supports jumbo frames up to 9001 bytes, whereas inter-Region peering supports 8500—then preserve Path MTU Discovery rather than assuming a local 9001-byte test proves the remote path.

Production scenario: symptom, competing hypotheses, and decision

A shared-services VPC B is peered with application VPC A and analytics VPC C. A reaches B, and C reaches B, but A cannot reach C. Engineers first add a broader route in A that points C's CIDR to the A-B peering connection. The route does not create transit because B cannot forward the packet from one peering connection to another. The correct decision is either a direct A-C peer with nonoverlapping CIDRs and reciprocal routes or a hub service designed for transit. During validation, a second symptom appears: an application in A resolves a public EC2 hostname in B to a public address. The team enables the appropriate peering DNS-resolution option and verifies VPC DNS attributes and policies. A final 9001-byte test succeeds inside one VPC but fails across an inter-Region peer, correctly pointing the team to the 8500-byte inter-Region ceiling and PMTUD rather than a security-group change.

Security, governance, scale, and failure boundaries

Peering creates reachability, not trust. Restrict who can request, accept, delete, and modify peering options and routes, and audit those actions with CloudTrail. Use narrow destination prefixes and least-privilege security-group rules; do not insert a default route toward a peer in the hope of using its egress edge because that topology is unsupported. Treat DNS-resolution changes as a security decision because private addressing can alter which endpoint a name selects. Inter-Region fabric encryption does not replace workload TLS, authentication, or authorization. Peering has no native inspection point, so a requirement for centralized stateful inspection, segmentation domains, or transitive service sharing may be a reason to choose Transit Gateway, Cloud WAN, VPC Lattice, or PrivateLink instead. Verify denied flows as well as permitted ones so a successful pairwise connection does not silently become broader lateral movement.

Essence / mental model

A Direct Connect gateway is a global AWS networking resource that associates Direct Connect virtual interfaces with virtual private gateways, Transit Gateways, or an AWS Cloud WAN core network. It behaves as a distributed set of BGP route reflectors outside the data path, so it does not become a Regional forwarding appliance or a separately duplicated gateway. High availability is inherent in that control role, while physical resilience still depends on independent Direct Connect connections, locations, customer routers, and BGP sessions. For Transit Gateway integration, a transit VIF attaches to the Direct Connect gateway and the gateway associates with the Transit Gateway. The allowed-prefix list on that association is not a learned-route filter in the conventional sense: those prefixes originate on the Direct Connect gateway and are advertised toward on-premises so traffic can be routed into the Transit Gateway even when its attached VPC CIDRs are not directly assigned to the gateway.

Architecture, dependencies, and normal flow

Separate physical-path resilience, BGP policy, gateway association, and workload segmentation. Multiple Transit Gateways in different Regions should use unique ASNs, and the design must account for documented quotas and unsupported combinations: a Direct Connect gateway already associated with a virtual private gateway or private VIF cannot simply be attached to a Transit Gateway. The point-to-point /30 used for connectivity does not propagate through a Transit Gateway. Across accounts, the Transit Gateway owner proposes the association and the Direct Connect gateway owner accepts it, retaining the ability to override the requested allowed prefixes. That ownership split is a route-governance boundary. Associations on one Direct Connect gateway normally cannot route to each other, but overlapping on-premises supernets and particular attachment arrangements can create VPC-to-VPC communication through the customer edge. Do not use that side effect as segmentation; use Transit Gateway route-table blackholes, specific advertisements, security policy, or separate gateways as required.

Essence / mental model

An AWS Cloud WAN segment is a routing domain expressed in the core network policy. It can exist at selected edge locations, require attachment acceptance, isolate attachments from one another, and filter which shared routes it accepts from other segments. The segment definition does not by itself decide where every VPC, VPN, Connect, Direct Connect gateway, or Transit Gateway route-table attachment belongs. Ordered attachment policies classify attachments using account, Region, attachment type, resource ID, tag key, or tag value conditions and then associate the first match with a segment or network function group. Once a rule matches, later rules are not evaluated for that attachment. This turns resource tags and rule numbers into routing inputs. Automatic association is convenient, but a tag change can move an attachment between trust zones unless the segment or rule requires acceptance.

Architecture, dependencies, and normal flow

Start with named routing and trust domains, not a list of VPCs. Decide whether members of a segment may communicate, which other segments may share routes, which Regions have core edges, and where human acceptance is mandatory. Isolated attachments cannot communicate with one another even in the same segment and cannot be reached from other segments; that setting is required for an intra-segment service-insertion pattern. Attachment policy rule numbers should leave insertion space and progress from specific high-trust matches to explicit catch-all handling. AND and OR conditions change classification materially, and network-function-group policies permit only tag name/value conditions with documented logic. Avoid a silent default that maps an untagged production attachment to development. Create a quarantine or pending segment, require acceptance for sensitive mappings, and treat the segment filter default—allow all shared routes—as a decision to review rather than a safe assumption.

Essence / mental model

DNSSEC signing lets validating resolvers verify that records came from the authoritative Route 53 hosted zone and were not modified. Route 53 signs zone responses with zone-signing keys that the service manages and rotates. The customer creates and manages a key-signing key backed by an asymmetric customer-managed AWS KMS key, then publishes a Delegation Signer record in the parent zone or registrar to establish the chain of trust. Enabling signing without the parent DS produces an island of trust: records are signed but public validators have no authenticated delegation from the parent. Publishing an incorrect DS, or leaving a DS after signing is disabled, can make the entire child zone bogus and unresolvable to validating clients. DNSSEC supplies origin authentication and integrity for DNS data; it does not encrypt queries, hide names, or prove the application at the returned address is trustworthy.

Architecture, dependencies, and normal flow

Prepare for failure before creating the KSK. Establish external availability checks, Route 53 query logging where appropriate, and CloudWatch alarms for DNSSECInternalFailure and DNSSECKeySigningKeysNeedingAction. Essence / mental model

AWS Network Firewall evaluates every packet against stateless rule groups before any stateful engine. Stateless rules inspect the packet in isolation using protocol, source and destination CIDRs, source and destination ports, and optional TCP flags. Rule groups are ordered by policy priority and rules inside a group by rule priority, both from the lowest number. The first match selects Pass, Drop, or Forward to stateful rules; a custom action can publish a metric in addition to one standard action. If no rule matches, the firewall uses separate policy defaults for full packets and UDP fragments. A packet forwarded to the stateful engine is then evaluated in flow context by Suricata-compatible policy. Critical network resources such as VPCs, Transit Gateways, route tables, Direct Connect associations, and security boundaries can be denied replacement or deletion while routine modifications remain allowed. A stack policy acts only during updates. Termination protection is a separate stack-level control that blocks direct DeleteStack. It does not stop an update from removing a nested stack or resource, which is why high-impact networks often need IAM, stack policy, change-set review, and termination protection together.

Essence / mental model

Security groups for Pods extend Amazon EC2 security-group policy from the node to selected EKS Pods. With ENABLE_POD_ENI, the VPC resource controller attaches a trunk ENI to a compatible Nitro-based Linux node and creates branch ENIs for matching Pods. A namespaced SecurityGroupPolicy selects Pods by pod labels or service-account labels and attaches one to five security groups; their rules are combined. This lets two applications on the same node have different VPC-level reachability to RDS, ElastiCache, or other services. It does not replace Kubernetes network policy or IAM identity. The enforcement mode materially changes egress identity: under strict behavior, Pod security groups govern outbound traffic and source NAT is disabled for relevant versions; under standard mode, traffic outside the VPC is normally source-NATed to the node primary ENI and evaluated by node security groups.

Architecture, dependencies, and normal flow

Choose compatible Linux EC2 instance types and VPC CNI versions; the feature is not available for Windows nodes or EKS Auto Mode.
