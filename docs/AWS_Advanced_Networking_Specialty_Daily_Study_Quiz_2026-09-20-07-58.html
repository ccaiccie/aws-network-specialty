Outposts local gateway routing modes: direct VPC routing versus customer-owned IP, BGP advertisements, overlap boundaries, and rollback

Primary feature lesson sourceLocal gateway route tables - AWS Outpostshttps://docs.aws.amazon.com/outposts/latest/userguide/routing.html

Classification/platform: Official AWS Outposts feature documentation. Source date: no update date displayed; checked 2026-09-20. Supports: The two mutually exclusive local-gateway routing modes, route-table associations, BGP advertisement behavior, NAT responsibilities, and direct-routing limitations.

Scenario support sourceCreate a CoIP pool - AWS Outpostshttps://docs.aws.amazon.com/outposts/latest/userguide/coip-pools.html

Classification/platform: Official AWS Outposts implementation guide. Source date: no update date displayed; checked 2026-09-20. Supports: The customer-owned IP pool workflow, allocation and association sequence, and operational objects used by the CoIP routing mode.

Essence / mental model

An Outposts rack local gateway connects Outposts subnets to the customer network, but the local gateway route-table mode determines which addresses cross that boundary. Direct VPC routing advertises Outposts subnet private IPv4 addresses over BGP and does not perform network address translation. Customer-owned IP routing instead uses an address pool supplied by the customer and associates a CoIP with a workload elastic network interface; the local gateway performs one-to-one translation between the workload private address and the CoIP. These modes are mutually exclusive for a local gateway route table, so they are architectural choices rather than per-packet preferences. The VPC route table, local-gateway route table, customer router, BGP advertisements, and return route must all express the same choice.

Architecture, dependencies, and normal flow

Choose direct VPC routing only when the on-premises routing domain can accept the Outposts subnet CIDRs without overlap. The local gateway advertises those private prefixes, and the customer network must return them to the correct Outpost. Choose CoIP when a customer-owned range provides the desired routable identity or isolates overlapping private space. Create the pool from the approved range, allocate addresses, and associate them with workload interfaces deliberately. CoIP translation does not remove the need for VPC routes, security groups, network ACLs, or customer-router policy. Direct routing also has workload limitations, including requester-managed network interfaces that are not reachable through the local gateway. Record which subnets are associated to which local-gateway route table before migration.

Classification/platform: Official AWS CLI implementation reference. Source date: no update date displayed; checked 2026-09-20. Supports: The tunnel inside IP version and outside IP address type inputs used to create a connection, plus option validation and resource relationships.

Essence / mental model

A Site-to-Site VPN has two address-family decisions: the outside tunnel transport and the inside traffic carried by the VPN. Virtual private gateways support the traditional IPv4 outside and IPv4 inside combination. Transit Gateway and Cloud WAN add combinations that can carry IPv6 inside traffic and can use IPv6 outside addresses where supported. A single VPN connection selects either IPv4 or IPv6 for its inside IP version; it does not carry both inside families simultaneously. IPv6 tunnel inside addressing uses /126 ranges. Existing VPN connections cannot simply have IPv6 enabled in place, so dual-stack migration is a connection-lifecycle design with parallel routing and cutover rather than an attribute toggle.

Architecture, dependencies, and normal flow

Start with the attachment target because it constrains the valid combinations. For a dual-stack application, plan separate VPN connections when both IPv4 and IPv6 inside traffic are required. Allocate nonconflicting tunnel inside ranges, choose BGP ASNs and advertised prefixes, and confirm the customer-gateway device supports the selected outside transport and MP-BGP behavior. An IPv6 outside transport is not available for every VPN form; private-IP VPN transport is a separate design with its own constraints. Build both tunnels per connection, avoid reusing inside addresses, and size route policy for independent IPv4 and IPv6 prefixes. Model MTU, PMTUD, firewalls, and return routing for each family rather than treating IPv6 as an alias for the IPv4 path.

Essence / mental model

A Cloud WAN Connect attachment integrates a routing appliance with a core network through an existing transport attachment. The protocol can be GRE or tunnel-less. Tunnel-less mode is represented as NO_ENCAP and removes GRE encapsulation, but it does not remove the attachment, peer, subnet, BGP, or route-policy layers. After the Connect attachment exists, a Connect peer is created for the appliance. The tunnel-less peer uses the appliance private IPv4 address and a selected subnet; IPv6 routes can be exchanged with MP-BGP, but the BGP session itself still depends on IPv4 unicast addressing. A routing-policy label can associate the attachment with policy intent, so labels and tags are control-plane inputs rather than documentation only.

Architecture, dependencies, and normal flow

Choose the transport VPC attachment and edge location first, then place the appliance close to the transport path; AWS recommends the same subnet as the transport VPC attachment for tunnel-less peers. Select NO_ENCAP only when the appliance and topology support direct routing without GRE. Set the peer ASN deliberately. When it differs from the core-network edge ASN, configure eBGP multihop with TTL 2. Define which prefixes the appliance may advertise and which core routes it should learn. A routing-policy label should be governed like a route-table association because policy can map matching attachments automatically. Build redundant appliances and peers across fault domains, and calculate throughput and return-path symmetry before making the attachment a production transit path.

Essence / mental model
