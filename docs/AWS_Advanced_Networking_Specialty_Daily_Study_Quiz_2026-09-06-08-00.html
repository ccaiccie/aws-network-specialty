VPC route-priority arbitration, overlapping prefix lists, and deterministic middlebox insertion

Primary feature lesson sourceHow route priority workshttps://docs.aws.amazon.com/vpc/latest/userguide/route-tables-priority.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-06. Source date: no update date displayed; checked 2026-09-06. Scenario support sourceExample routing optionshttps://docs.aws.amazon.com/vpc/latest/userguide/route-table-options.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-06. Source date: no update date displayed; checked 2026-09-06. Supports: Concrete gateway and inter-subnet middlebox routes, source/destination-check requirements, and unsupported routing loops.

Essence / mental model

The reliable mental model for an Amazon VPC route table is a deterministic destination lookup, not a sequence of rules read from top to bottom. IPv4 and IPv6 are evaluated independently. The router first chooses the most-specific matching destination. Only when destinations are identical do origin and target precedence rules matter: a static route to targets such as an internet gateway, NAT gateway, network interface, transit gateway, peering connection, gateway endpoint, or Gateway Load Balancer endpoint wins over a dynamically propagated route. A route that references a prefix list also wins over an equally specific propagated route. An especially dangerous edge case is two different prefix-list routes whose expanded entries overlap at the same prefix length and point to different targets: AWS chooses one route, then keeps that choice, but the design should not treat the initial selection as intentional policy. Route order in the console does not repair ambiguity.

Architecture, dependencies, and normal flow

Start with a destination-to-target intent table and prove every relevant prefix before creating routes. Preserve the VPC local route unless the documented middlebox pattern requires replacing its target, and prefer exact subnet-CIDR routes when steering east-west traffic. Inbound inspection uses a gateway route table associated with the internet gateway or virtual private gateway; that table can send a destination subnet CIDR to an appliance ENI. The appliance must live in a separate subnet from the source or destination, have source/destination checking disabled when it forwards traffic, and have a viable onward and return path. Hosts in the same subnet cannot be forced through an appliance by VPC route tables because their communication does not traverse the subnet router. Avoid sending traffic from AWS-managed services back toward the subnet containing that service through a middlebox, which AWS documents as unsupported and unpredictable. Model return symmetry explicitly when the middlebox is stateful.

Essence / mental model

Direct Connect resiliency is an end-to-end path property, not a count of ports. The Resiliency Toolkit presents maximum resiliency, high resiliency, and development/test models so engineers can align independent connections, devices, and locations with an availability objective. Maximum resiliency uses separate connections terminating on separate devices in more than one Direct Connect location and is the topology associated with the 99.99% SLA when every SLA condition is met. High resiliency uses two single connections across multiple locations and aligns with a 99.9% objective when its conditions are met. Development/test separation across devices in one location protects against a device failure but not a location failure. The toolkit assists with ordering and placement, yet carrier paths, customer routers, power, cross-connects, BGP policy, gateway attachment, and application routing can still share a hidden fate.

Architecture, dependencies, and normal flow

Map each physical and logical element to a failure domain: customer router, carrier, meet-me room, Direct Connect device, location, virtual interface, Direct Connect gateway or virtual private gateway/transit gateway, and destination Region. Keep redundant connections at compatible capacity and ensure the customer network can actually use the secondary advertisements. Prefer BGP so the failed virtual interface withdraws reachability, then make local preference, AS path, and allowed-prefix filters support the intended primary/backup or active/active design. A Site-to-Site VPN may provide an additional backup class, but its bandwidth and path policy must be tested rather than assumed. SLA eligibility is not automatic merely because a diagram resembles a model; validate the current SLA requirements and every dependency.

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-06. Source date: no update date displayed; checked 2026-09-06. Supports: The implementation sequence for an IGMP domain, subnet associations, host IGMP version, and static addition of non-IGMP members.

Essence / mental model

Transit Gateway multicast provides one-to-many delivery between subnets of attached VPCs while the transit gateway acts as the multicast router. A multicast domain is the segmentation object; subnet associations decide which attachment subnets participate. Group membership is ultimately represented by ENIs. In an IGMP domain, supported hosts dynamically join and leave with IGMPv2, and members may send and receive. In static membership designs, the API or CLI registers source ENIs and member ENIs. Static-sources support narrows which registered ENIs may send; when it is disabled in a static-member design, instances in associated subnets may send while only registered members receive. This control plane is distinct from unicast Transit Gateway route tables. A multicast group address identifies the replication group, while associated subnets establish the domain boundary and ENIs establish membership.

Architecture, dependencies, and normal flow

Enable multicast when creating a new transit gateway; it cannot be retrofitted onto an existing one. Choose IGMP or static membership based on host capability and operational ownership. A subnet can belong to only one multicast domain, so align domains with security and application boundaries before onboarding. AWS supports IGMPv2; many EC2 operating systems default to IGMPv3, so the host configuration must be deliberate. Non-Nitro instances require source/destination checking disabled and cannot be multicast senders. Transit Gateway multicast is not carried over Direct Connect, Site-to-Site VPN, peering attachments, or Connect attachments, so it cannot transparently extend an on-premises multicast domain. There is no Transit Gateway fragmentation for multicast; size datagrams to the supported path MTU. AWS cautions that the feature may not suit high-frequency-trading or other performance-sensitive applications, and quotas must be reviewed.

Essence / mental model

A Route 53 private hosted zone is a DNS authority visible only through associated VPC resolution contexts. It is not a globally private copy of a public zone. The VPC Resolver evaluates associated private hosted zones, Resolver rules, and public DNS using specific precedence. Split-view DNS uses public and private zones with the same name so internal and external clients can receive different answers. Inside an associated VPC, the most-specific matching private namespace is authoritative. If that private zone matches the queried name but lacks the requested record and type, Resolver returns NXDOMAIN; it does not fall through to the public hosted zone. This negative boundary is essential: creating a private example.com zone shadows public example.com names for associated VPCs unless the necessary internal records exist.

Architecture, dependencies, and normal flow

Enable both enableDnsSupport and enableDnsHostnames on the VPC. Associate every intended VPC with the zone, including the required authorization and API workflow for cross-account associations. Design namespace ownership before records: decide which suffix is served in Route 53, which remains public, and which is forwarded to on-premises authorities. Overlapping private hosted zones use the most-specific match. A Resolver forwarding rule for the same domain takes precedence over a private hosted zone, so careless conditional forwarding can silently bypass Route 53 records. When custom DNS servers are placed on instances, they must forward private AWS names to the Amazon-provided resolver address for the VPC or to Resolver endpoints as designed. Private hosted zones support a defined subset of routing policies, including simple, failover, multivalue, weighted, latency, geolocation, and geoproximity.

Once its state transitions from PENDING to AVAILABLE, integrations can target an ALB or NLB listener ARN, or an AWS Cloud Map service whose discovered instances include IP addresses and ports. The API, VPC link, and target resource must be owned by the same AWS account. This is application-layer proxying into a VPC, not general VPC routing and not a PrivateLink endpoint service. API Gateway authorization governs who invokes the API; VPC routing, security groups, load-balancer health, service discovery, TLS, and backend authorization govern the private hop.

Architecture, dependencies, and normal flow

Create the VPC link in resilient subnets and a least-privilege security group before creating the integration. VPC link V2 subnet and security-group selections are immutable, so replacement is the migration mechanism. For an ALB or NLB, provide the listener ARN—not the load balancer ARN or target-group ARN—to an HTTP_PROXY integration. For Cloud Map, API Gateway calls DiscoverInstances and sends requests among healthy returned resources; ECS registrations need usable IP/port attributes, commonly through SRV service discovery or ECS Service Connect. Private integration traffic uses HTTP by default; supply tlsConfig and the expected secure server name for HTTPS to the backend. API Gateway prepends the stage name to the backend path by default; parameter mapping to $request.path removes it when the application expects the original path.

Normal-state check: the configured Workload and service integration control point, its dependency chain, and its return/response behavior must all agree. Treat an available control-plane object as evidence of configuration state—not proof that the workload data path, name resolution, target process, or authorization layer works.

The source links above are the authoritative field and service-behavior references.

Change boundary: configuration objects, routes or name-resolution decisions, policy controls, and application targets are separate layers. A healthy result at one layer never authorizes skipping checks at the next.

Production scenario: symptom, competing hypotheses, and decision

A production HTTP API returns 404 from a healthy ALB backend only in the deployed prod stage. The VPC link is AVAILABLE and security groups allow traffic. API Gateway is forwarding /prod/orders while the backend expects /orders. Use request parameter mapping to overwrite the path with $request.path rather than changing routes or widening security groups. In a second environment an API used only for annual reporting fails after 60 days of no traffic. The VPC link is INACTIVE because API Gateway deleted its ENIs. New traffic triggers reprovisioning, which can take minutes; monitor state until AVAILABLE and design a warm-up or availability plan if cold reactivation is unacceptable.

Evidence interpretation

Track VPC link state, ENI existence, subnet IP capacity, security-group egress, listener and target health, Cloud Map discovery results, integration error metrics, access logs, and backend logs. The documented CLI creates the link with subnet and security-group IDs, then create-integration binds connection type VPC_LINK and the link ID to a listener or service ARN. An AVAILABLE link proves the managed network interfaces exist; it does not prove the listener, service-discovery attributes, TLS server name, stage path, or application is correct. Test the exact API route and log the path that reaches the backend.

Security, governance, scale, and failure boundaries

Keep invocation authorization and backend reachability as separate controls. Use JWT, IAM, Lambda authorizers, or other supported API Gateway methods as required, then restrict VPC link security-group egress to intended private targets. For HTTPS private integrations, validate the backend server name through tlsConfig rather than silently downgrading to HTTP. Protect VPC link and integration mutations with IAM and CloudTrail. Same-account ownership is an architectural boundary; do not simulate unsupported cross-account targeting with overly broad routing. Apply WAF where supported for the chosen API type and protect backend services from direct paths that bypass API controls.

For high availability, use the feature’s documented multi-AZ/Region or multi-path capabilities where applicable, maintain an intentional rollback, and record account ownership. Revisit quotas, supported IP families, protocol/platform version constraints, and cost/scale implications in the cited AWS documentation before production expansion.
