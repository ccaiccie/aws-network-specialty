Elastic IP address transfer between AWS accounts with a two-party, Regional handoff and explicit rollback

Primary feature lesson sourceTransfer an Elastic IP address between AWS accounts - Amazon Elastic Compute Cloudhttps://docs.aws.amazon.com/AWSEC2/latest/UserGuide/transfer-EIPs-intro-ec2.html

Classification/platform: Official Amazon EC2 feature documentation. Source date: no update date displayed; checked 2026-09-18. Supports: The two-step transfer workflow, same-Region boundary, seven-day acceptance window, address state constraints, quota behavior, exclusions, and rollback controls.

Scenario support sourceaccept-address-transfer — AWS CLI Command Referencehttps://docs.aws.amazon.com/cli/latest/reference/ec2/accept-address-transfer.html

Classification/platform: Official AWS CLI implementation reference. Source date: no update date displayed; checked 2026-09-18. Supports: The target-account acceptance call, allocation ID returned in the target account, and the dry-run and authorization behavior used in an operational handoff.

Essence / mental model

Elastic IP transfer moves an Amazon-owned public IPv4 address from one AWS account to another without changing the address that customers, partners, or DNS records use. It is a two-party handoff, not a resource share: the source account enables transfer for an unassociated address and the target account accepts it in the same AWS Region. Acceptance gives the target a new allocation ID and removes control from the source. The enabled state expires after seven days, which limits how long an unfinished handoff can remain available. The source must communicate the address and approved window out of band because the pending transfer is not discoverable from the target account.

Architecture, dependencies, and normal flow

Treat the public address as a production identity with dependent DNS, allow-lists, reverse DNS, certificates, monitoring, and incident ownership. Inventory those dependencies before enabling transfer. The source must disassociate the address and remove any reverse DNS record; the target must have Elastic IP quota and an association plan. Transfer is Regional and does not move tags. Addresses from BYOIP, customer-owned pools, or IPAM contiguous blocks are outside this workflow. Build an explicit rollback gate: before acceptance the source can disable the transfer; after acceptance a rollback is a new transfer in the other direction and therefore needs another reviewed window.

Classification/platform: Official AWS implementation and verification guide. Source date: no update date displayed; checked 2026-09-18. Supports: End-to-end test sequencing, BGP and tunnel checks, instance routing and security dependencies, and evidence needed to verify the hybrid data path.

Essence / mental model

A virtual private gateway chooses a route by specificity and then by AWS-defined route-source priority. The immutable local VPC route protects the VPC CIDR, even when a propagated path is more specific. For equal prefixes, a route-table static target such as an Internet gateway, NAT gateway, network interface, peering connection, or gateway endpoint takes precedence over propagated routes. Among propagated hybrid routes of identical prefix length, Direct Connect BGP is preferred over Site-to-Site VPN static routes, which are preferred over Site-to-Site VPN BGP. Within comparable BGP choices, AS_PATH and MED help select a path, while tunnel health can override an otherwise preferred route.

Architecture, dependencies, and normal flow

Design primary and backup paths from the full ordered decision, not from BGP attributes alone. If Direct Connect should be primary and VPN standby, advertise the same prefixes and avoid a more-specific VPN announcement that unintentionally wins by longest prefix. A virtual private gateway forwards only prefixes it knows and does not provide ECMP, so two equally attractive VPN tunnels do not become an aggregate multipath design. Configure and monitor both tunnels because AWS maintenance can affect either. Model the reverse path separately: on-premises routers may apply a different best-path algorithm, creating asymmetry through stateful firewalls even when AWS selects the intended outbound path.

Essence / mental model

A transit gateway owner can share the gateway through AWS Resource Access Manager so participant accounts can create VPC attachments without owning the transit gateway itself. Sharing delegates attachment creation, not routing authority. The transit gateway owner controls its route tables, associations, propagations, and acceptance settings. A participant controls its VPC attachment resources and VPC subnet route tables; either side can delete an attachment. Each attachment associates with one transit gateway route table but can propagate routes to multiple tables. This split is the foundation for a governed multi-account hub: the owner defines connectivity domains while participants connect only approved VPCs and selected subnets.

Architecture, dependencies, and normal flow

Choose an Organizations or principal scope for the RAM share and decide whether attachment requests are auto-accepted. Auto-accept accelerates a tightly governed organization; manual acceptance adds a useful approval boundary when account posture or requested VPC CIDRs must be reviewed. Define route-table domains before onboarding: production, non-production, inspection, and shared services often need different associations and propagations. VPC route tables must still point intended prefixes to the attachment, and the transit gateway tables need a valid forward and return path. Reject overlapping CIDRs up front because attachment availability does not resolve ambiguous addressing.

Essence / mental model

Route 53 Traffic Flow is a visual and API-driven way to compose complex public DNS routing as a tree of routing rules and endpoints. A traffic policy is a reusable definition; each edit creates a version rather than mutating an existing version. A policy record applies one version to a DNS name in a public hosted zone. Route 53 then creates and manages the underlying records represented by the tree, while the policy record is the deployment handle shown in the console. This separation gives DNS engineers a reviewable policy artifact, immutable version history, and fast rollback without manually editing every generated record.

Architecture, dependencies, and normal flow

Use Traffic Flow when nested latency, failover, weighted, geolocation, geoproximity, or multivalue decisions would be difficult to maintain as independent record sets. Design the root rule, its branches, health evaluations, endpoint types, TTLs, and default coverage before deployment. Traffic Flow policy records apply to public hosted zones, so private hybrid name resolution needs a different design. Keep endpoint identifiers and routing logic environment-neutral when reusing a policy. Version limits and monthly policy-record charges matter at scale; aliases to supported AWS resources can reduce query charges, but policy records themselves remain billed while present.
