1. Amazon VPC foundations · Network Design / Implementation

Dual-stack private-subnet egress with route-table intent

Primary feature lesson source:NAT gateways - Amazon VPCAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.htmlPublic and private NAT gateway behavior, source translation, and route-table placement.
Scenario support source:Example dual-stack VPC configurationAWS Documentation examplehttps://docs.aws.amazon.com/vpc/latest/userguide/vpc-migrate-ipv6-example.htmlThe distinct IPv4 NAT-gateway and IPv6 egress-only-internet-gateway routes in a private subnet.

Essence / mental model

A route table is a per-subnet forwarding policy, not a statement that a subnet is “public” or “private.” A subnet becomes operationally public only when its selected route table has a path to an internet gateway and its resources have usable public addressing. Dual stack makes the decision twice: IPv4 and IPv6 are independent forwarding domains.

Start from the selected route table, then trace the target. A private dual-stack subnet commonly sends 0.0.0.0/0 to a NAT gateway and ::/0 to an egress-only internet gateway. The NAT gateway handles address translation for IPv4; the egress-only gateway provides stateful, outbound-only IPv6 reachability without translating IPv6 addresses. The local routes remain the path for VPC CIDRs.

Healthy design is explicit: associate every workload subnet with a purpose-built route table instead of relying on the main table. Put a public NAT gateway in a subnet whose route table leads to an internet gateway. For regional resilience, create a NAT gateway per Availability Zone and route each private subnet to its same-AZ NAT gateway; that avoids an AZ dependency and inter-AZ data path for normal egress.

Common mistakes are treating a security group as a substitute for routing, adding only IPv4 egress in a dual-stack subnet, or assuming a NAT gateway's Elastic IP is used for non-internet destinations. The right troubleshooting order is route-table association, longest-prefix target, target state, security controls, and then DNS/address family.

Evidence and interpretation

0.0.0.0/0 → nat-gateway-id
::/0 → egress-only-internet-gateway-id

What this proves: The private subnet has distinct default egress paths for IPv4 and IPv6.

What this does not prove: It does not prove the NAT gateway is in a public subnet, that its public subnet reaches an internet gateway, or that security rules allow the flow.

Next discriminating check: Inspect the NAT gateway subnet route table and test DNS answers and traffic separately for A and AAAA records.

Source-grounded engineering scenario

A private dual-stack application can reach an IPv4 SaaS endpoint but fails to reach an IPv6-only endpoint. IPv4 Flow Logs are normal. The discriminating check is the workload subnet’s ::/0 route: it must use an egress-only internet gateway, not the IPv4 NAT gateway. The root-cause class is address-family-specific routing, not a generic internet outage. Verify with an IPv6 destination after the route is corrected.

Feature principle being tested: Route selection and egress mechanisms are address-family specific.

Design / operations takeaways

  • Associate workload subnets explicitly.
  • Model IPv4 and IPv6 paths independently.
  • Use a same-AZ NAT gateway pattern when resilience and cost predictability matter.

2. Hybrid connectivity · Network Design / Operations

Direct Connect and Site-to-Site VPN BGP path control

Primary feature lesson source:Direct Connect routing policies and BGP communitiesAWS Documentationhttps://docs.aws.amazon.com/directconnect/latest/UserGuide/routing-and-bgp.htmlAWS routing-policy behavior and BGP community use with Direct Connect virtual interfaces.
Scenario support source:Troubleshoot routing issues - AWS Direct ConnectAWS troubleshooting documentationhttps://docs.aws.amazon.com/directconnect/latest/UserGuide/ts-routing.htmlA BGP session can be established while prefix advertisement or downstream routing still prevents traffic flow.

Essence / mental model

A healthy BGP session proves adjacency, not end-to-end reachability. Hybrid designs must deliberately choose which prefixes are advertised, which path is preferred, and what happens when the preferred attachment is impaired.

Direct Connect uses virtual interfaces and BGP to exchange reachable prefixes. Private, public, and transit virtual interfaces have different attachment and route-policy implications. On premises, treat BGP attributes and advertisement policy as the contract: advertise only owned and intended prefixes, retain a route-policy record, and avoid using a broad summary that creates unexpected reachability.

A common design uses Direct Connect as the normal private path and Site-to-Site VPN as a resilient alternate. That does not work merely because both are attached: selection must be intentional at both ends. AWS Direct Connect documentation describes route-policy and community mechanisms; your on-premises policy must be consistent with those decisions. Keep BGP timers, maximum-prefix controls, and failover testing in the operating runbook.

When BGP is up but applications fail, do not immediately reset the peer. Compare advertised and received prefixes, inspect the VPC/TGW routing domain, and confirm return traffic uses a valid path. The test should distinguish a missing prefix from a route preference, security, NAT, or DNS problem.

Evidence and interpretation

BGP Established plus no usable route for the on-premises application prefix

What this proves: The peering transport and BGP control session are up.

What this does not prove: It does not prove the desired prefix was advertised, accepted, propagated to the attachment, or selected for return traffic.

Next discriminating check: Compare the advertised/received prefix sets and the effective VPC or Transit Gateway route table.

Source-grounded engineering scenario

A private virtual interface is up and its BGP peer is Established, yet traffic to 10.40.0.0/16 never reaches the data center. The Direct Connect troubleshooting guidance makes prefix advertisement the first discriminating check. If the customer router does not advertise that prefix, AWS has no return path even though the neighbor looks healthy. Remediate the export policy, then confirm route appearance and bidirectional packet flow.

Feature principle being tested: BGP state, route exchange, route selection, and forwarding are separate layers.

Design / operations takeaways

  • Monitor prefix state as well as BGP state.
  • Design a preferred and backup path explicitly.
  • Test return-path behavior during every hybrid failover exercise.

3. Transit and multi-VPC networking · Network Design / Implementation

Transit Gateway route domains, association, propagation, and appliance mode

Primary feature lesson source:How AWS Transit Gateway worksAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.htmlTransit Gateway attachment and routing concepts, including security integration.
Scenario support source:Avoiding asymmetric routing with AWS Network FirewallAWS troubleshooting / design documentationhttps://docs.aws.amazon.com/network-firewall/latest/developerguide/asymmetric-routing.htmlWhy forward and return traffic must traverse the same inspection design and how appliance mode helps preserve endpoint symmetry.

Essence / mental model

An attachment is connected to exactly one Transit Gateway route table through association; propagation is how routes become candidates in route tables. Treat route tables as separate reachability domains, not as an incidental list of routes.

Use associations to decide which Transit Gateway route table evaluates traffic that arrives from an attachment. Use propagation or static routes to define where that attachment’s prefixes appear. This makes segmentation explainable: production spokes can learn shared-services routes without learning development routes, and an inspection attachment can be used as the next hop for selected prefixes or defaults.

Central inspection designs require more than a default route to a security VPC. The return direction must also be routed through the inspection attachment. For stateful Network Firewall or appliance paths, appliance mode supports flow symmetry at the Transit Gateway side so a return packet is not steered to a different inspection endpoint.

Operationally, inspect the attachment association first, then the matching route table and its propagations/static routes. Do not infer a route from the fact that two VPCs are attached. A healthy attachment can remain intentionally isolated.

Evidence and interpretation

Attachment association → one TGW route table
Propagation/static route → reachable prefix in a route domain

What this proves: You can explain which table evaluates ingress from an attachment and why a route is or is not present.

What this does not prove: It does not prove the spoke VPC subnet route tables target the TGW or that return traffic uses the same inspection path.

Next discriminating check: Check both the Transit Gateway route table and the source/destination VPC subnet route tables.

Source-grounded engineering scenario

East-west application traffic crosses a centralized firewall successfully in one direction but the return packet is dropped after being delivered to a different firewall endpoint. The Network Firewall guidance identifies asymmetric routing as the failure class. Route both directions through the firewall attachment and enable appliance mode where the TGW inspection architecture requires endpoint symmetry. Verify a complete 5-tuple flow, not just one ICMP probe.

Feature principle being tested: Transit Gateway segmentation and stateful inspection depend on deliberately paired forward and return routes.

Design / operations takeaways

  • Association chooses the ingress route table.
  • Propagation does not replace subnet routing.
  • Stateful inspection is a two-direction route design problem.

4. DNS and service discovery · Network Design / Operations

Route 53 health checks, DNS failover, and resolver reachability

Primary feature lesson source:Creating Amazon Route 53 health checksAWS Documentationhttps://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover.htmlHealth-check types and DNS failover mechanics.
Scenario support source:Configuring router and firewall rules for Route 53 health checksAWS troubleshooting documentationhttps://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover-router-firewall-rules.htmlHealth checks need network access to the monitored endpoint, including appropriate security-group or prefix-list rules.

Essence / mental model

Route 53 DNS failover changes what DNS answers it returns. It does not repair application state, override resolver caching, or prove a target is reachable from every client network.

For failover records, Route 53 uses health status to choose whether to return primary or secondary records. Health checks can monitor endpoints, calculated health, or CloudWatch-alarm data. Design the check around the actual service boundary: a TCP listener can be healthy while the application is not, and a CloudWatch alarm can represent an application signal instead of a public probe.

DNS is a control plane with caching. A correct failover record does not instantaneously change every client; recursive resolver TTL behavior still matters. For private service discovery, use private hosted zones and Resolver endpoints deliberately. Cross-network resolution requires routing and UDP/TCP 53 access, not merely a private hosted zone.

When a health check is unhealthy, first prove whether Route 53 can reach the configured endpoint and port. Then confirm the health-check association and failover record. Avoid testing with a stale DNS answer and calling the record policy wrong.

Evidence and interpretation

Primary health check healthy → Route 53 returns primary record
Primary unhealthy + secondary healthy → Route 53 returns secondary record

What this proves: The DNS answer selection rule is behaving as configured.

What this does not prove: It does not prove the client resolver has expired its cached answer or that the endpoint provides an application-level success response.

Next discriminating check: Query authoritative and recursive paths separately; verify the configured health-check port and security-group allowance.

Source-grounded engineering scenario

A failover record never moves to secondary even though a load balancer target is known unhealthy. The check was pointed at a different endpoint and its security group blocks Route 53 health checkers. The relevant repair is to correct the monitored endpoint/port and admit the documented health-check source range or managed prefix list. Verify the health check itself before interpreting DNS results.

Feature principle being tested: DNS failover relies on the health signal Route 53 can actually observe.

Design / operations takeaways

  • Separate health-signal validity from DNS-cache behavior.
  • Allow health-check traffic to the configured endpoint.
  • Use private DNS design with Resolver routing and security controls, not assumptions.

5. Private service access · Network Design / Security

Interface endpoints, private DNS, endpoint policies, and cross-account services

Primary feature lesson source:Configure an interface endpoint - Amazon VPCAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/privatelink/interface-endpoints.htmlPrivate DNS prerequisites, endpoint ENIs, security groups, and endpoint configuration.
Scenario support source:How do I use VPC endpoints to access Amazon S3 buckets?AWS Knowledge Centerhttps://repost.aws/knowledge-center/s3-vpc-endpointsGateway endpoint route-table behavior and common access validation checks.

Essence / mental model

PrivateLink is selective private connectivity, not a general substitute for all routing. An interface endpoint is an ENI in selected subnets; DNS and the endpoint ENI security group determine whether clients actually use and reach it.

For an AWS service interface endpoint, private DNS can make the public service hostname resolve to the endpoint’s private addresses inside a VPC. The VPC must have DNS resolution and DNS hostnames enabled. The endpoint ENI security group must allow the client traffic, commonly inbound HTTPS from the workload security group. Network ACLs and client routing must still permit the path.

Gateway endpoints differ: S3 and DynamoDB gateway endpoints insert service-prefix-list routes into chosen route tables rather than creating ENIs. Endpoint policies restrict what the endpoint may access; they are not a replacement for IAM or resource policies. For provider-owned endpoint services, service acceptance, allowed principals, supported AZs, and private-DNS ownership verification are separate control points.

When private access fails, identify endpoint type first. Then test DNS resolution, selected endpoint/subnet availability, endpoint security group, endpoint policy, IAM/resource policy, and service name/Region. Avoid hard-coding endpoint IP addresses because AWS supplies DNS names for a reason.

Evidence and interpretation

Private DNS requires VPC DNS hostnames + DNS resolution
Interface endpoint ENI security group allows expected inbound HTTPS

What this proves: A workload can resolve the service name privately and has a network control path to the endpoint ENI.

What this does not prove: It does not prove endpoint policy, IAM, bucket policy, or service authorization permits the requested API action.

Next discriminating check: Use DNS lookup and a denied/allowed API call to separate transport from authorization.

Source-grounded engineering scenario

An EC2 instance in a private subnet cannot call STS after an interface endpoint is created. The endpoint exists, but private DNS was not enabled and the endpoint security group admits no TCP 443 from the instance. The correct diagnosis separates name resolution from ENI reachability. Enable private DNS where appropriate, allow the workload security group to the endpoint ENI, then verify the API call and CloudTrail evidence.

Feature principle being tested: Private service access is DNS, ENI reachability, endpoint policy, and identity authorization working together.

Design / operations takeaways

  • Identify interface versus gateway endpoint behavior.
  • Use service DNS names, not endpoint IPs.
  • Test network reachability and authorization as separate hypotheses.

6. Load balancing and service insertion · Network Implementation / Security

Gateway Load Balancer placement, health, and flow symmetry

Primary feature lesson source:Gateway Load BalancersAWS Documentationhttps://docs.aws.amazon.com/elasticloadbalancing/latest/gateway/introduction.htmlGateway Load Balancer’s role as a managed insertion and distribution point for virtual appliances.
Scenario support source:Using Gateway Load Balancer with Transit Gateway for centralized network securityAWS Whitepaperhttps://docs.aws.amazon.com/whitepapers/latest/building-scalable-secure-multi-vpc-network-infrastructure/using-gwlb-with-tg-for-cns.htmlCentral inspection architecture, AZ affinity, appliance mode, and failure behavior.

Essence / mental model

Gateway Load Balancer is an insertion service for appliance fleets. It helps distribute flows to healthy appliances, but routing must still lead traffic to a GWLB endpoint and return it to the correct next hop.

ALB, NLB, and GWLB solve different problems. ALB routes HTTP(S) requests at Layer 7; NLB distributes Layer 4 connections; GWLB inserts a fleet of virtual appliances into the path. In a GWLB design, endpoints are routeable targets in workload or security VPCs, while targets behind the GWLB are the appliance fleet. The service and appliance are separate availability responsibilities.

A practical centralized design pairs Transit Gateway routing with a security VPC containing GWLB endpoints and appliances. Appliance mode and paired forward/return paths protect stateful flows. Availability Zone behavior matters: by default, GWLB has AZ affinity, and cross-zone choices alter failure and cost tradeoffs. A healthy target group is necessary but does not prove the surrounding VPC/TGW route tables use it.

Troubleshoot from the route target inward: confirm the source route points to the correct GWLB endpoint, then GWLB endpoint status, target health, appliance listener/GENEVE handling, return route, and the stateful appliance policy. A packet capture at one appliance cannot prove symmetric return traffic.

Evidence and interpretation

Spoke route → GWLB endpoint → GWLB target appliance → return GWLB endpoint

What this proves: The intended inspection insertion chain is defined.

What this does not prove: It does not prove target health, appliance policy, cross-AZ behavior, or reverse routing is correct.

Next discriminating check: Validate one complete TCP connection in both directions and compare AZ/attachment selection.

Source-grounded engineering scenario

A spoke can reach a destination through a firewall appliance, but long-lived TCP sessions reset only after return traffic begins. The whitepaper’s appliance-mode guidance identifies a likely symmetry failure. Validate both Transit Gateway directions and the GWLB endpoint used in each AZ. Remediate the route domain and appliance-mode setting, not the application listener.

Feature principle being tested: Service insertion must preserve a stateful, bidirectional path.

Design / operations takeaways

  • Choose ALB/NLB/GWLB by traffic role, not name similarity.
  • Health checks do not replace route validation.
  • Model AZ affinity and reverse flow before deployment.

7. Edge and global traffic delivery · Network Design / Security

Route 53 and Global Accelerator health-driven regional failover

Primary feature lesson source:How failover works for unhealthy endpoints - AWS Global AcceleratorAWS Documentationhttps://docs.aws.amazon.com/global-accelerator/latest/dg/about-endpoints-endpoint-weights.unhealthy-endpoints.htmlGlobal Accelerator endpoint-group failover behavior and the effect of endpoint weight.
Scenario support source:How Amazon Route 53 chooses records when health checks are configuredAWS Documentationhttps://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-how-route-53-chooses-records.htmlPrimary/secondary DNS-answer behavior when health checks change state.

Essence / mental model

Global traffic control is a choice between DNS answers and static Anycast entry points. Route 53 changes answers at DNS time; Global Accelerator accepts traffic at static IPs and makes endpoint-group decisions. Both depend on health configuration that represents the application boundary.

Route 53 failover, weighted, latency, and geolocation policies operate at DNS resolution time. Their response changes are subject to client and recursive resolver caching. Global Accelerator provides static Anycast IP addresses and routes traffic through the AWS global network to healthy endpoint groups. It can fail over beyond an endpoint group when healthy weighted endpoints exist elsewhere.

Design the health signal first. A target can pass a low-level port check while the application is unusable. Route 53 can use endpoint, calculated, or CloudWatch-alarm health checks. Global Accelerator health access must be permitted to its configured health-check port; endpoint weight and traffic dial are separate concepts from health.

When a regional failover looks wrong, inspect health state, endpoint weight, traffic dial, security group, and whether the client is still using a cached DNS response. Do not use a single client lookup to infer the authoritative record state.

Evidence and interpretation

Global Accelerator: no healthy weighted endpoint in a group → seek healthy endpoint in another group
Route 53: primary unhealthy + secondary healthy → return secondary

What this proves: The service has a defined health-driven selection behavior.

What this does not prove: It does not prove a client has refreshed DNS or that the application itself is semantically healthy.

Next discriminating check: Inspect health-check reachability and query the appropriate DNS/accelerator control-plane state.

Source-grounded engineering scenario

A Global Accelerator endpoint appears available but receives no new traffic during a regional incident. The only healthy endpoint has weight zero. Global Accelerator’s documented failover behavior seeks healthy endpoints with weight greater than zero. Correct the endpoint weight, validate health-check ingress, and run a controlled regional failover test.

Feature principle being tested: Health, weight, traffic percentage, and client DNS caching are different levers.

Design / operations takeaways

  • Choose DNS or Anycast entry based on traffic-control needs.
  • Keep a health signal aligned to user-visible availability.
  • Test endpoint weights and health-check ingress before an event.

8. Network inspection and perimeter protection · Network Security / Implementation

AWS Network Firewall placement, state, and return-path symmetry

Primary feature lesson source:Filter network traffic using AWS Network FirewallAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/userguide/network-firewall.htmlStateful and stateless Network Firewall rule-group behavior.
Scenario support source:Avoiding asymmetric routing with AWS Network FirewallAWS Network Firewall troubleshooting documentationhttps://docs.aws.amazon.com/network-firewall/latest/developerguide/asymmetric-routing.htmlForward and return traffic must remain in the intended inspection path for stateful rules.

Essence / mental model

Network Firewall is stateful only when the network design returns a flow to the same inspection context. Its policies decide what to allow or drop; route tables decide whether packets encounter that policy at all.

Network Firewall supports stateless and stateful rule groups. Stateless rules evaluate packets in isolation, while stateful rules track traffic in flow context. The firewall endpoint is inserted through routing, so its placement in an ingress, egress, or centralized inspection VPC must be represented in every relevant route table.

For centralized east-west or hybrid inspection, deploy endpoints in the Availability Zones that serve the workloads and use Transit Gateway route tables that send both directions through the inspection attachment. Appliance mode is relevant for preserving endpoint symmetry in Transit Gateway designs. An otherwise healthy firewall can drop return packets if the return path bypasses it or lands at a different endpoint.

Investigate packet direction and routing before changing Suricata or domain rules. Prove source route, firewall endpoint, policy action, return route, and target response. Network Firewall observability can tell you whether a packet reached the firewall; it cannot explain a packet that never routes there.

Evidence and interpretation

Stateless rule group → packet-level criteria
Stateful rule group → flow-context inspection

What this proves: The selected policy type determines whether protocol/session state is part of inspection.

What this does not prove: It does not prove the traffic is actually routed through the firewall endpoint or returns symmetrically.

Next discriminating check: Check every forward and return route-table target before editing firewall rules.

Source-grounded engineering scenario

A centralized firewall logs the initial SYN but no successful handshake for a spoke-to-spoke flow. The policy is permissive. The discriminating check is the reverse TGW route: it points directly to the source attachment rather than the firewall attachment. The root cause is bypassed return inspection. Repair the paired route and use appliance mode where the design requires it; then validate a complete bidirectional flow.

Feature principle being tested: Stateful filtering needs stateful path symmetry.

Design / operations takeaways

  • Rules and routes are separate controls.
  • Design endpoint coverage per AZ.
  • Troubleshoot the return path before relaxing a policy.

9. Network access control and governance · Network Security / Compliance

Security groups, network ACLs, and layered network controls

Primary feature lesson source:Control traffic to your AWS resources using security groupsAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.htmlSecurity-group attachment, stateful behavior, and rule semantics.
Scenario support source:Example: Control access to instances in a subnetAWS Documentation examplehttps://docs.aws.amazon.com/vpc/latest/userguide/nacl-examples.htmlNACL ordering, statefulness difference, and explicit return rules compared with security groups.

Essence / mental model

Security groups are stateful, ENI-level allow controls. Network ACLs are stateless, subnet-level ordered allow/deny controls. They are complementary layers with very different troubleshooting logic.

Use security groups as the primary control for resource access. A rule can reference another security group, which makes application-tier intent clearer than static CIDRs. Return traffic for allowed flows is automatically permitted because security groups are stateful. Security groups do not provide an explicit deny rule.

Use NACLs when a subnet-wide, stateless guardrail or explicit deny is appropriate. NACL rules are evaluated in ascending rule number order, and return traffic needs a matching rule in the opposite direction. This makes ephemeral-port planning important for client/server flows. A permissive security group does not override an NACL deny.

Endpoint policies, IAM, resource policies, AWS Firewall Manager, and Organizations add governance around network access. Do not attribute an authorization denial to a security group merely because the TCP connection succeeds. Diagnose control planes in order: route, NACL, security group, endpoint policy, identity, resource policy.

Evidence and interpretation

Security group: stateful, allow rules
Network ACL: stateless, ordered allow/deny rules

What this proves: A return-flow issue can legitimately appear only at the NACL layer even when the security group looks correct.

What this does not prove: It does not prove the route table, endpoint policy, IAM decision, or target application is correct.

Next discriminating check: Trace one 5-tuple in both directions and evaluate NACL rule order before altering a security group.

Source-grounded engineering scenario

SSH reaches an instance through a security group rule, but the session cannot establish. The subnet NACL allows inbound TCP 22 but denies all outbound traffic, including the ephemeral return port. The AWS example documents that NACLs need an outbound response rule. Add the constrained return range, then verify the security group remains least privilege.

Feature principle being tested: Stateful and stateless controls require different return-path reasoning.

Design / operations takeaways

  • Use security groups for primary workload policy.
  • Use NACLs deliberately as subnet guardrails.
  • A successful TCP handshake does not prove API authorization.

10. Network observability and operations · Network Management and Operation

Flow Logs, CloudWatch delivery, and Reachability Analyzer

Primary feature lesson source:Logging IP traffic using VPC Flow LogsAWS Documentationhttps://docs.aws.amazon.com/vpc/latest/userguide/flow-logs.htmlVPC Flow Logs scope and publication to CloudWatch Logs, S3, or Firehose.
Scenario support source:Troubleshoot VPC Flow LogsAWS troubleshooting documentationhttps://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-troubleshooting.htmlDelivery failures, IAM trust/permissions, rate limits, and status fields.

Essence / mental model

Flow Logs are telemetry about selected VPC IP traffic; Reachability Analyzer is static configuration analysis. Together they support a hypothesis, but neither alone is an application packet capture or a time machine.

VPC Flow Logs can capture information about traffic to and from ENIs, subnets, or VPCs and publish records to CloudWatch Logs, S3, or Firehose. Plan the scope and destination before an incident because Flow Logs cannot retroactively show traffic that occurred before logging was enabled. Use custom formats and retention consciously; not all traffic types are recorded.

Reachability Analyzer examines configuration to construct a virtual hop-by-hop path or identify a blocking component. It is especially useful for missing route-table entries, security-group/NACL issues, and supported network constructs. It is static analysis, so it does not prove a remote application process is accepting traffic or that a transient runtime condition did not occur.

When logs go quiet, inspect the flow-log status and DeliverLogsErrorMessage, then the destination IAM role/trust relationship and destination quotas. When connectivity fails, compare Flow Log observation with a Reachability Analyzer path. A REJECT record, a configuration block, and a server listener failure are different root-cause classes.

Evidence and interpretation

Flow Logs destination: CloudWatch Logs, S3, or Firehose
DeliverLogsErrorMessage: delivery diagnostics

What this proves: A configured collection pipeline exists and may expose delivery-state errors.

What this does not prove: It does not prove every packet is logged or that the application completed its protocol exchange.

Next discriminating check: Check record scope/time window and pair runtime flow evidence with a static Reachability Analyzer path.

Source-grounded engineering scenario

A network team reports that Flow Logs stopped arriving. The Flow Log configuration shows an access error. AWS documents that missing log-publishing permissions or a wrong trust relationship can cause this state. Restore the delivery role and trust, confirm status becomes active, then generate controlled traffic and verify a new record arrives.

Feature principle being tested: Telemetry delivery health is itself an operational dependency.

Design / operations takeaways

  • Enable telemetry before the incident.
  • Separate telemetry delivery errors from traffic denies.
  • Pair static path analysis with observed flow data.

11. Deployment and automation · Network Implementation / Management

CloudFormation dependency ordering and safe network changes

Primary feature lesson source:AWS::EC2::Route - AWS CloudFormationAWS CloudFormation Template Referencehttps://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ec2-route.htmlRoute resource properties and the explicit gateway-attachment dependency required in relevant templates.
Scenario support source:AWS::EC2::VPCGatewayAttachment - AWS CloudFormationAWS CloudFormation Template Referencehttps://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ec2-vpcgatewayattachment.htmlThe gateway attachment resource whose lifecycle must precede dependent routes.

Essence / mental model

Infrastructure as code makes network intent repeatable only when the dependency graph matches service reality. A route can be syntactically valid and still fail if its target attachment has not been created.

CloudFormation expresses network objects as resources and infers many dependencies from references. Some VPC routes need an explicit DependsOn relationship to an internet-gateway attachment or virtual-private-gateway attachment when both are in the same template. Treat this as a control-plane ordering requirement, not an arbitrary CloudFormation quirk.

Safe network delivery starts with stable logical IDs, parameterized CIDRs/Regions, change-set review, least-privilege deployment roles, and an explicit rollback plan. Separate foundational topology from high-risk route/policy changes when blast radius warrants it. For multi-account environments, keep account/Region context visible in templates and deployment logs.

After a deployment, verify the resulting control plane: resource status, intended route entries, attachment state, and data-plane reachability. A successful stack update only proves CloudFormation reached a terminal state; it does not prove the intended traffic path, DNS name, or policy effect was validated.

Evidence and interpretation

AWS::EC2::Route DependsOn: gateway attachment when required

What this proves: The route is not attempted before its referenced gateway attachment is available.

What this does not prove: It does not prove the route table is associated with the intended subnet or that traffic policy allows the resulting path.

Next discriminating check: Review the change set, then validate resource state and a representative data-plane flow after deployment.

A stack intermittently fails while creating an internet route. The route resource refers to an IGW, but the attachment has no explicit dependency. The CloudFormation reference documents this dependency case. Add DependsOn to the route, deploy through a change set, then validate the public-subnet association and route target.

Feature principle being tested: Declarative resources still have real control-plane ordering.

Design / operations takeaways

Amazon EKS VPC CNI pod IP capacity and subnet design

Primary feature lesson source:Assign IPs to Pods with the Amazon VPC CNIAWS Documentationhttps://docs.aws.amazon.com/eks/latest/userguide/managing-vpc-cni.htmlHow the VPC CNI allocates ENIs and VPC IPv4/IPv6 addresses for Pods.
Scenario support source:Increase the available IP addresses for your Amazon EKS nodesAWS troubleshooting / configuration documentationhttps://docs.aws.amazon.com/eks/latest/userguide/cni-increase-ip-addresses-procedure.htmlPrefix-delegation configuration and the <code>InsufficientCidrBlocks</code> fragmentation condition.

Essence / mental model

With the Amazon VPC CNI, pod scheduling consumes VPC address capacity. Kubernetes scaling, ENI limits, subnet free addresses, contiguous prefixes, and security-group scope can all become networking constraints.

The Amazon VPC CNI runs on EKS nodes and creates or uses ENIs to give Pods VPC-routable IPv4 or IPv6 addresses. This is operationally powerful because Pods are first-class network endpoints, but it means a cluster can run out of usable subnet or ENI capacity before CPU or memory is exhausted.

Prefix delegation can improve available pod address capacity by assigning prefixes to ENIs instead of allocating individual secondary addresses repeatedly. It has prerequisites and a fragmentation risk: a subnet can have free individual addresses but lack a contiguous /28 block. Custom networking can place Pod ENIs in alternate subnets, but it changes the routing and security design you must document.

For a failed Pod launch, distinguish Kubernetes scheduling from AWS address allocation. Inspect CNI logs, node ENI/IP limits, subnet free capacity and CIDR reservations, CNI version compatibility, and network-policy/security-group controls. Do not simply enlarge a node group when the actual constraint is an exhausted or fragmented Pod subnet.

Evidence and interpretation

InsufficientCidrBlocks: subnet lacks enough contiguous /28 blocks for prefix delegation

What this proves: Prefix allocation is constrained by contiguous address space, not only by the raw count of free addresses.

What this does not prove: It does not prove node CPU/memory, Kubernetes scheduling policy, or an application readiness issue is the blocker.

Next discriminating check: Inspect CNI logs, ENI/IP limits, subnet fragmentation, and the cluster’s CNI mode/version.

Source-grounded engineering scenario

Pods remain Pending while the subnet dashboard shows free IP addresses. CNI logs show InsufficientCidrBlocks after prefix delegation is enabled. The source guidance identifies fragmentation as the distinction: create a new suitable subnet or reserve CIDR space for prefix use, then add/rebalance nodes under the supported migration guidance. Verify new prefix allocation and pod address assignment.

Feature principle being tested: Cloud workload scaling can be limited by network address topology before compute limits.

Design / operations takeaways

  • Plan pod subnet capacity as part of cluster design.
  • Differentiate free IP count from contiguous prefix availability.
  • Treat CNI version and networking mode as production dependencies.
