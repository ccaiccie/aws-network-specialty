Essence / mental model

The VPC owner controls VPC-level constructs, subnets, routes, and network ACLs; participants create and manage supported application resources that they own in shared subnets. Participants can attach their own security groups to ENIs they own but cannot inspect or modify another participant's resources merely because those resources share the subnet. Availability Zone names are account-relative, so multi-account placement must compare stable Availability Zone IDs. Changing an owner-managed route or ACL can affect participant workloads without transferring ownership, so shared change control, evidence, and rollback contracts are mandatory. The advanced design task is to separate control-plane configuration, data-plane behavior, identity authorization, name resolution, and workload state. Production scenario: symptom, competing hypotheses, and decision

A participant service loses reachability after the network account changes a shared-subnet route table, and each team sees only its own resources. Competing hypotheses include stale client state, a routing or DNS defect, an identity-policy denial, a security control, and application failure. The decisive root cause is: The owner changed a shared routing dependency without a participant-aware rollout, while the runbook assumed participants could inspect the route table. The corrective sequence is: Map control ownership, compare AZ IDs, export owner-side route and ACL evidence, restore the recorded route, test participant ENIs and security groups separately, and gate changes on cross-account canaries. The team first captures a failing transaction with timestamps and stable identifiers, then changes one layer, repeats both positive and negative tests, and compares the evidence. Rollback restores the recorded configuration, not a reconstructed guess.
