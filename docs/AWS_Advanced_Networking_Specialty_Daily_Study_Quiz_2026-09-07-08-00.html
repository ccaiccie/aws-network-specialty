Secondary CIDR association lifecycle, overlap gates, and route injection in an existing VPC

Primary feature lesson sourceVPC CIDR blockshttps://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-07. Source date: no update date displayed; checked 2026-09-07. Supports: IPv4 and IPv6 CIDR association constraints, local-route behavior, quotas, states, and disassociation boundaries.

Scenario support sourceAdd or remove a CIDR block from your VPChttps://docs.aws.amazon.com/vpc/latest/userguide/add-ipv4-cidr.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-07. Source date: no update date displayed; checked 2026-09-07. Supports: The console and API workflow, association-state verification, dependent subnet cleanup, and rollback mechanics.

Essence / mental model

A VPC CIDR association changes the address and routing envelope of an existing VPC. An IPv4 VPC begins with a primary block, normally between /16 and /28, and can receive secondary IPv4 blocks; IPv6 associations are separate. When a CIDR becomes associated, AWS adds or updates the VPC-local route in every route table so addresses in the associated ranges can communicate through the VPC router. This is not equivalent to resizing the primary block: the primary IPv4 CIDR cannot be changed or removed. Association is an asynchronous state machine, so an API acceptance is not the same as the associated state. Address planning must consider overlap with existing VPC ranges, peering, Transit Gateway, Direct Connect gateway associations, propagated routes, and every network that may later need connectivity.

Architecture, dependencies, and normal flow

Plan the secondary range as part of an enterprise IP hierarchy before allocating subnets. The block must not overlap another CIDR already associated with the VPC, and AWS also evaluates documented route and connectivity conflicts. A secondary block that is locally unique but overlaps a route to an on-premises network can make the desired hybrid path impossible or ambiguous. Existing peering states and Direct Connect gateway associations impose additional gates because AWS must protect deterministic routing. The default quotas for IPv4 and IPv6 CIDRs per VPC can be adjusted, but quota headroom does not make overlapping ranges routable. For IPv6, choose the provider and network-border-group model deliberately, and remember that dual-stack security groups, network ACLs, DNS, and egress behavior remain separate design decisions.

A merger workload needs 4,000 more private addresses. An engineer proposes associating 10.48.0.0/20 because it is unused inside the VPC, but the route tables already send 10.48.0.0/16 to a Transit Gateway for a data-center estate. Direct Connect link aggregation groups: LACP membership, minimum-links safeguards, and true failure domains

Primary feature lesson sourceAWS Direct Connect link aggregation groupshttps://docs.aws.amazon.com/directconnect/latest/UserGuide/lags.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-07. Source date: no update date displayed; checked 2026-09-07. Supports: LAG eligibility, LACP active-active behavior, supported connection counts, capacity, and minimum-links semantics.

Scenario support sourceUpdate a LAGhttps://docs.aws.amazon.com/directconnect/latest/UserGuide/update-lag.html

Classification/platform: Official AWS service documentation · current online guide · checked 2026-09-07. Source date: no update date displayed; checked 2026-09-07. Supports: How minimum links is changed and how the threshold can intentionally take the entire logical interface down.

Essence / mental model

A Direct Connect link aggregation group combines dedicated physical connections into one logical interface using LACP. Eligible member connections must terminate at the same Direct Connect endpoint in the same location, use the same bandwidth, and satisfy AWS connection-count limits. All member links operate active-active; a LAG is not an active-standby bundle. The logical capacity is the sum of active member capacity, subject to traffic hashing and the bandwidth of each individual flow. AWS supports dedicated connection speeds including 1, 10, 100, and 400 Gbps, with lower maximum member counts for the highest speeds. A LAG simplifies configuration and adds link-level capacity or protection, but every member still shares a location and endpoint failure domain.

Architecture, dependencies, and normal flow

Use a LAG when the requirement is more bandwidth at one Direct Connect endpoint or protection from an individual member-link failure. Do not count it as location diversity. A resilient hybrid architecture normally combines the LAG with an independent connection or LAG at another Direct Connect location, diverse customer routers and carriers, and routing policy that can move traffic. LACP distributes flows by a hash; it does not stripe a single flow byte-by-byte, so aggregate tests and single-flow tests answer different questions. The minimum-links attribute is an availability guard: if too few member links remain active, AWS marks the LAG down instead of allowing a severely under-capacity path to keep attracting production traffic. Set that threshold from workload capacity and failover behavior, not from a desire to keep the console green.

Normal-state check: the configured Hybrid connectivity control point, its dependency chain, and its return/response behavior must all agree. Essence / mental model

Transit Gateway security-group referencing lets an inbound security-group rule in one attached VPC name a security group associated with instances in another attached VPC, including supported cross-account designs in the same Region. It replaces brittle source CIDRs with workload identity at the security-group layer, but it does not create routing. The source and destination VPCs must already communicate through the same Transit Gateway. The feature is controlled twice: security-group referencing must be enabled on the Transit Gateway and on every participating VPC attachment. The Transit Gateway setting is disabled by default, while attachment defaults differ, so checking only one layer is a common failure. The feature applies to inbound references; it does not make outbound cross-VPC references a general mechanism.

Architecture, dependencies, and normal flow

Use references when application tiers move between addresses or accounts but remain within one Regional Transit Gateway routing domain. Enable the gateway option deliberately, opt in only attachments that need the behavior, and keep route-table segmentation. The rule still belongs to the destination security group: for example, the database group allows inbound TCP 3306 from the application-tier group. Both IPv4 and IPv6 instance traffic can benefit because membership, not a CIDR literal, is referenced. Current boundaries matter: references do not cross Regions, Transit Gateway peering, multicast, Gateway Load Balancer, Network Firewall, or third-party bump-in-the-wire appliances. If inspection is required in the path, use CIDR/prefix-list policy at that boundary or redesign the enforcement architecture instead of assuming the identity survives the middlebox.

Essence / mental model

A Route 53 Resolver inbound endpoint gives DNS resolvers outside a VPC private IP destinations for queries that AWS Resolver should answer. AWS creates an endpoint IP address and elastic network interface in each selected subnet. An on-premises resolver forwards chosen suffixes to those IPs over Direct Connect or Site-to-Site VPN; Resolver then evaluates private hosted zones, VPC DNS data, forwarding rules, and public recursion according to the endpoint type and namespace. Security groups must allow the intended TCP and UDP DNS traffic. The endpoint is not a DNS server running on an EC2 instance, and an endpoint state of operational proves neither the enterprise conditional forwarder nor the network return path.

Architecture, dependencies, and normal flow

Deploy endpoint IPs in at least two Availability Zones and point on-premises conditional forwarders at all approved addresses. Use default inbound endpoints for the general hybrid pattern. A delegation inbound endpoint supports a delegated subdomain model and requires the surrounding DNS hierarchy, including NS delegation and glue/address records, to be correct. Keep namespace ownership explicit: forward only domains that AWS Resolver is expected to answer, and avoid loops with outbound endpoints or reciprocal catch-all rules. Hybrid routing must carry queries to the endpoint ENIs and responses back to the resolver. Because DNS normally begins with UDP but can retry over TCP for large or truncated answers, permit and test both protocols on port 53 unless the documented workload boundary says otherwise.

Architecture, dependencies, and normal flow

The performance objective matters: ENA Express targets high single-flow bandwidth and tail latency under congestion, while ordinary enhanced networking may be preferable for very high packet-per-second workloads that optimize uncongested median latency. Both endpoints need compatible configuration, so enabling only the sender creates silent standard-ENA fallback. Plan host MTU and buffers, especially for UDP, because SRD headers reduce effective MTU and TCP MSS clamping does not solve every UDP payload.

Normal-state check: the configured Workload networking control point, its dependency chain, and its return/response behavior must all agree. Treat an available control-plane object as evidence of configuration state—not proof that the workload data path, name resolution, target process, or authorization layer works.
