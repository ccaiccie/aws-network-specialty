DNS64 and NAT64 for controlled IPv6-only subnet access to IPv4 services

Primary feature lesson sourceDNS64 and NAT64https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-nat64-dns64.html

Scenario support sourceIntroducing dual-stack and IPv6-only support for Amazon Route 53 Resolver endpointshttps://aws.amazon.com/blogs/networking-and-content-delivery/introducing-dual-stack-and-ipv6-only-support-for-amazon-route-53-resolver-endpoints/

Classification/platform: Official AWS Networking & Content Delivery implementation article. Source date: no update date displayed; checked 2026-09-15. Supports: A hybrid DNS pattern in which IPv6-only clients reach IPv4 Resolver endpoint addresses through DNS64, a 64:ff9b::/96 route, and a private NAT gateway.

Essence / mental model

DNS64 and NAT64 solve a narrow translation problem: an IPv6-only workload must initiate a connection to a destination that has only an IPv4 address. When DNS64 is enabled on the workload subnet, the Amazon-provided resolver checks the requested name. If the authoritative answer has no AAAA record but does have an A record, the resolver synthesizes an IPv6 answer by embedding the IPv4 address in the well-known 64:ff9b::/96 prefix. The client opens an IPv6 connection to that synthesized address. A subnet route for 64:ff9b::/96 sends the packet to a NAT gateway, whose NAT64 behavior translates it into IPv4. This is different from ordinary IPv6 internet access: an egress-only internet gateway handles native IPv6 destinations, whereas NAT64 is used for the synthesized prefix. Translation is a reachability mechanism, not DNS authority, application authorization, or a guarantee that every library behaves correctly with IPv6.

Architecture, dependencies, and normal flow

Enable DNS64 on the exact IPv6-only subnets that need translation and keep AmazonProvidedDNS in the resolution path. Add 64:ff9b::/96 to the workload subnet route table with the intended NAT gateway as target. A public NAT gateway can reach public IPv4 destinations through an internet gateway; a private NAT gateway is appropriate when the IPv4 destination is reached through Transit Gateway, a virtual private gateway, or other private connectivity. Do not place the NAT gateway route back toward the same source in a way that creates a loop. Keep native IPv6 traffic on its own ::/0 design, typically through an egress-only internet gateway for outbound-only internet access. For hybrid DNS, decide whether an IPv6 Resolver endpoint, DNS64, or native dual-stack authority is the correct dependency. The console exposes DNS64 as a subnet attribute; the CLI equivalent is modify-subnet-attribute with enable-dns64.

Essence / mental model

A Site-to-Site VPN connection has two tunnels because endpoint maintenance and isolated failures are normal operating conditions. Tunnel endpoint lifecycle control gives an operator earlier visibility into AWS-initiated maintenance and a supported way to apply a pending replacement during a chosen window before the mandatory deadline. The control is per tunnel, identified by the VPN connection and outside IP address. Enabling it on an existing tunnel can itself trigger replacement unless the documented skip-tunnel-replacement option is used. The central mental model is therefore lifecycle state plus redundant forwarding: a maintenance API can coordinate when one endpoint changes, but uninterrupted service still depends on the second tunnel, route convergence, and a customer gateway that actually uses both paths.

Architecture, dependencies, and normal flow

Enable lifecycle control consistently and record whether the initial replacement is skipped. Query get-vpn-tunnel-replacement-status before scheduling work; checking status does not download or apply the update. Apply pending maintenance with replace-vpn-tunnel only after the alternate tunnel carries a representative data path. For fleet scale, consume AWS Health events with EventBridge, notify through SNS, and schedule Systems Manager Automation during an approved window. In a multi-account organization, a delegated networking account can assume a narrowly scoped member-account role that is permitted to inspect and replace only the intended tunnel. Build idempotency around VPN connection ID, outside IP, event ARN, deadline, and current replacement status. Never let one event trigger both tunnel replacements in parallel.

Transit Gateway route-table association, propagation, static precedence, and blackhole containment

Primary feature lesson sourceTransit gateway route tables in AWS Transit Gatewayhttps://docs.aws.amazon.com/vpc/latest/tgw/tgw-route-tables.html

Classification/platform: Official AWS Transit Gateway architecture and task documentation. Source date: no update date displayed; checked 2026-09-15. Supports: Attachment association, multi-table propagation, static routes, backup use, and supported attachment types.

Scenario support sourceCreate a static route in AWS Transit Gatewayhttps://docs.aws.amazon.com/vpc/latest/tgw/tgw-create-static-route.html

Classification/platform: Official AWS Transit Gateway implementation procedure. Source date: no update date displayed; checked 2026-09-15. Supports: Active and blackhole static-route creation plus the warning that static routes to VPN attachments are not filtered by Site-to-Site VPN.

Essence / mental model

A Transit Gateway route table answers one directional question: after a packet enters through an attachment, which attachment should receive the destination prefix? Each attachment is associated with one route table, and that associated table is consulted for traffic arriving from the attachment. An attachment can propagate its prefixes into multiple route tables. Static entries can target an attachment or intentionally blackhole a prefix. When an equally specific static and propagated route compete, the static route has priority; removing it can reveal the propagated route again. These mechanics make route tables a segmentation control, but only when association and propagation are treated as separate relationships. A route appearing in a table does not tell you which source attachments consult that table.

Architecture, dependencies, and normal flow

Model route domains before configuring individual routes: production spokes, shared services, inspection, hybrid, and isolation. Associate every ingress attachment with exactly the table whose policy it should use. Enable propagation only where the attachment's prefixes are intended to be learned; Transit Gateway propagation cannot filter individual advertised routes. Use an explicit static route when a deterministic next hop or blackhole is required, and document how static precedence affects a dynamic backup. Be cautious with a static route targeting a VPN attachment because the VPN does not filter it in the way some operators assume. Pair every forward path with a return path and include the VPC subnet route tables on both sides. Export or search routes before and after a change to make hidden precedence visible.

Primary feature lesson sourceWeighted routinghttps://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html

Classification/platform: Official Amazon Route 53 routing-policy documentation. Source date: no update date displayed; checked 2026-09-15. Supports: Weight calculation, same-name/type sets, zero-weight behavior, health-check interactions, TTL and recursive-resolver effects.

Scenario support sourceTroubleshoot DNS resolution issues with a weighted routing policyhttps://repost.aws/knowledge-center/route-53-fix-dns-weighted-routing-issue

Classification/platform: AWS re:Post Knowledge Center troubleshooting article. Source date: no update date displayed; checked 2026-09-15. Supports: Operational checks for record weights, health, resolver caches, TTL, and observed answer ratios.

Essence / mental model

Weighted routing distributes Route 53 answers among records that share a name and type. The probability for one record is its weight divided by the sum of weights in the set; weights are values from 0 through 255, not percentages that must total 100. A zero-weight record is normally excluded while positive-weight records are eligible, which makes zero useful for a standby or a deliberately drained endpoint. Health checks change the eligible set. If all positive-weight records are unhealthy and a healthy zero-weight record exists, Route 53 can return the zero-weight record. Recursive resolvers cache answers for the configured TTL, so one client or one resolver does not observe a statistically independent Route 53 choice on every request.

Architecture, dependencies, and normal flow

Create all records with the same DNS name, type, and routing policy, give each a unique set identifier, and choose weights that express relative—not absolute—traffic. Attach health checks or evaluate-target-health only where the health signal reflects the endpoint. For a canary, use a small nonzero weight and a TTL that balances responsiveness with query volume; recognize that resolver population and client behavior can produce noisy ratios. For active-standby, understand the zero-weight health interaction instead of assuming zero means never returned. Do not combine alias and non-alias records incompatibly or expect weighted policy to keep individual user sessions sticky. When multi-Region endpoints have different capacity, coordinate weight with autoscaling and failure limits.

For an edge-optimized custom domain, the ACM certificate must be in us-east-1 because CloudFront uses it. For a Regional custom domain, the certificate belongs in the API's Region. Creating the API or custom domain does not create the public DNS record; map the custom name to the API Gateway domain target. Define base-path or API mappings and routing mode explicitly. A public custom domain cannot be attached directly to a private API as though the boundary were interchangeable. During edge-to-Regional migration, provision the target domain configuration and DNS path, test host and stage mappings, lower TTL, and keep rollback until traffic and TLS evidence converge.

Normal-state check: the configured Workload and service integration control point, its dependency chain, and its return/response behavior must all agree. Treat an available control-plane object as evidence of configuration state—not proof that the workload data path, name resolution, target process, or authorization layer works.

Private APIs require interface endpoint reachability and resource policies that authorize intended VPC endpoints or principals; private does not mean automatically authorized.
