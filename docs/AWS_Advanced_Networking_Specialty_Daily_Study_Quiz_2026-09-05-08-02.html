Consulted 2026-09-05. This distinct source supports the operational condition applied in the scenario; it is not used as a substitute for the feature lesson.

Essence / mental model

Amazon VPC IP Address Manager (IPAM) is a control system for address intent, allocation, observation, and history. Its useful mental model is not “an address spreadsheet in AWS,” but a hierarchy of scopes, pools, allocations, and discovered resources. Scopes separate routing and security domains; pools express delegable address plans; allocations show which CIDRs have been handed to resources or child pools. That hierarchy lets a network team convert policies such as Region, environment, business unit, mask length, and non-overlap into allocation rules rather than relying on human memory. IPAM can monitor resource use against those rules, retain assignment history, and allocate VPC CIDRs automatically. The data plane still follows VPC route tables and security controls—IPAM governs address provenance and compliance but does not forward packets.

Architecture, dependencies, and normal flow

Design the hierarchy before enabling automation. A global pool can be subdivided by routing domain, then Region, environment, and workload boundary. The hierarchy should mirror where overlapping space is permitted and where summarization is expected. Operating Regions determine where IPAM discovers and manages resources, while delegated administration through AWS Organizations can centralize visibility across accounts. Choose the public or private scope deliberately and identify owners for pool delegation, allocation rules, and remediation. For IPv4 exhaustion, track utilization and fragmentation; for IPv6, treat large allocations as policy objects even when address abundance is not the constraint. A managed prefix list is a consumer of CIDR truth, not the source of truth: it can feed security-group references and route tables after IPAM resolves which resources or pool CIDRs match a rule.

Security, governance, scale, and failure boundaries

Delegated address administration is powerful: restrict creation of pools, changes to allocation rules, and resolver-to-prefix-list targets. Essence / mental model

MAC Security (MACsec) on AWS Direct Connect protects the Ethernet cross-connect between a compatible customer edge interface and the Direct Connect device. It provides confidentiality, integrity, and data-origin authenticity at Layer 2 while Layer 3 routing such as BGP continues above it. The boundary matters: MACsec is hop-by-hop protection for this point-to-point link, not end-to-end encryption across the campus, carrier path beyond the supported handoff, VPC, or application. AWS derives a short-lived Secure Association Key from the configured Connectivity Association Key Name and Connectivity Association Key pair. Direct Connect supports static CAK mode, and the session key is regenerated automatically. Operations therefore distinguish long-term CKN/CAK lifecycle from transparent SAK rotation.

Architecture, dependencies, and normal flow

Start with physical eligibility. MACsec is available on supported dedicated connections and appropriate partner interconnects or link aggregation groups, not hosted connections. The customer router interface must be MACsec capable; supported speeds and cipher requirements vary, and high-speed links require extended packet numbering. Secure Channel Identifier is required. Then choose an encryption mode as a business decision. must_encrypt refuses traffic when MACsec cannot be established and is appropriate when unencrypted fallback is unacceptable. should_encrypt attempts encryption but can fall back to clear traffic; it favors availability during commissioning but requires monitoring so silent fallback is not mistaken for compliance. New MACsec-enabled connections default to should_encrypt, so a compliance design must not assume fail-closed behavior without checking the mode.

For rotation, exploit the documented keychain behavior rather than replacing the only working key. Essence / mental model

Transit Gateway Connect integrates third-party virtual appliances—commonly SD-WAN routers—with AWS Transit Gateway using GRE for the data path and BGP for dynamic routing. A Connect attachment is layered on an existing VPC or Direct Connect attachment called the transport attachment. A Connect peer is the GRE tunnel. Each peer establishes two BGP sessions to AWS-managed infrastructure; AWS accumulates routing information from both, so loss of one control session should not interrupt routing. That pair is control-plane redundancy inside one peer, not two equal-cost data paths. Appliance-side high availability uses multiple Connect peers or appliances, each with its own redundant BGP sessions, plus equivalent advertisements when ECMP is desired.

Architecture, dependencies, and normal flow

Address three layers separately: the underlay transport, the GRE outer endpoints, and the BGP inside addresses. The transit gateway requires a CIDR block from which its GRE address is drawn; the appliance peer GRE address must share the address family. Inside IPv4 BGP addressing uses a unique /29 from the 169.254.0.0/16 link-local range, excluding documented reserved blocks, and optional IPv6 prefixes are exchanged through MP-BGP. The first address of the /29 is configured on the appliance. If the appliance ASN differs from the transit gateway ASN, configure eBGP multihop with TTL 2. Static routes on Connect are not the fallback—Connect uses BGP. For multiple appliance peers to be ECMP candidates, advertised prefixes, ASNs, and AS-PATH attributes must be compatible.

Essence / mental model

Route 53 Resolver DNS Firewall filters outbound DNS queries that originate in associated VPCs. The policy object is a rule group associated with a VPC; rules point to domain lists or advanced threat-detection behavior and specify actions such as allow, alert, or block. DNS Firewall evaluates rules by numeric priority until a matching terminating decision applies, so ordering is part of the security design. It governs name-resolution requests through the VPC Resolver. It does not inspect the subsequent TCP or UDP application connection, replace endpoint authorization, or guarantee that blocking one name prevents access by another name or direct IP address. Think of it as a DNS decision point within a layered egress architecture.

Architecture, dependencies, and normal flow

Create separate rule groups for controls with different owners or deployment cadence, and associate them with the correct VPCs in every required Region. Start with explicit organizational allow requirements, then curated threats and custom deny rules, while ensuring priorities express the intended override behavior. AWS Managed Domain Lists are maintained threat sets for malware, botnet command-and-control, aggregated threats, and GuardDuty-derived domains. Their contents cannot be browsed or edited, so rollout requires telemetry. DNS Firewall Advanced can add protections for suspicious algorithms and tunneling, but it still needs a false-positive and change process. Use Resolver query logging or firewall logs for evidence, and keep rule-group association inventory aligned with account vending.

In bidirectional mode it blocks traffic to and from internet gateways and egress-only internet gateways, except for approved exclusions. In ingress-only mode it blocks inbound internet traffic while preserving outbound patterns that use NAT gateways or egress-only internet gateways. Exclusions can apply to a VPC or subnet and can permit bidirectional or, under bidirectional account mode, egress-only behavior. BPA is a guardrail above workload routing—not a replacement for least-privilege routes, security groups, or application policy.

Architecture, dependencies, and normal flow

Choose the mode from an explicit enterprise internet-access model. A data-processing estate might use bidirectional block with a small number of egress-only exclusions. A general application estate may start with ingress-only to retain managed outbound updates while preventing direct inbound paths. Inventory every internet-facing load balancer, public web tier, bastion, third-party integration, NAT egress VPC, and IPv6 egress design before enforcement. VPC BPA is Regional, so coverage automation must address all enabled Regions. Exclusions are part of the design, not an emergency escape hatch: assign owners, direction, scope, and expiry. Use Network Access Analyzer and BPA status reporting to identify resources whose current path depends on an internet gateway.

Essence / mental model

Amazon VPC Traffic Mirroring copies selected packets from a supported elastic network interface to an out-of-band monitoring target. Four objects define the function: source ENI, mirror filter, target, and session. The copied stream is VXLAN encapsulated, leaving the original workload path independent of the analyzer. Filters and packet truncation control volume and privacy. Targets can be an analyzer ENI, a Network Load Balancer, or a Gateway Load Balancer endpoint; load-balanced targets improve availability but can deliver mirrored packets out of order. Mirroring is evidence capture, not an inline allow/deny control, and a missing mirrored packet is not automatically proof the production packet never existed.

Architecture, dependencies, and normal flow

Place load-balanced targets across at least two Availability Zones and consider cross-zone load balancing for failure tolerance.
