Essence / mental model

MTU is a path property before it is a host tuning value. Every EC2 instance supports a 1500-byte MTU and current-generation instances support 9001-byte jumbo frames, but an end-to-end flow can use only the smallest MTU on its path. AWS documents important ceilings: traffic through an internet gateway or VPN is limited to 1500 bytes, while inter-Region VPC peering has an 8500-byte limit. A 9001-byte interface therefore does not establish that a 9001-byte packet can reach a destination. Path MTU Discovery closes the gap by returning an ICMP signal when a packet is too large. IPv4 uses Destination Unreachable, fragmentation needed, type 3 code 4 when the Don't Fragment bit is set. IPv6 routers do not fragment in transit; they return ICMPv6 Packet Too Big, type 2, and the source must send smaller packets. If those signals are filtered, small exchanges such as SYN packets can work while larger TLS records, replication batches, or database responses stall. The correct mental model is interface MTU, path bottleneck, feedback signal, and transport adaptation—not merely a number on eth0.

Architecture, dependencies, and normal flow

Use jumbo frames where the whole path supports them, such as tightly controlled same-VPC or Direct Connect designs whose virtual interface and on-premises equipment were validated. Keep internet- and VPN-bound traffic at 1500 unless a route-specific design deliberately selects another interface. AWS explicitly describes using per-route MTU configuration or multiple elastic network interfaces with different MTUs to keep high-throughput east-west traffic at 9001 while sending constrained traffic through a 1500-byte path. The dependency chain includes the guest operating system, ENA driver, subnet network ACL, security group connection tracking, any middlebox, transit component, VPN or inter-Region boundary, and the remote host. Security groups may allow tracked PMTUD responses, but a network ACL can still discard ICMP. IPv6 needs special care because there is no in-network fragmentation fallback. Treat an MTU change as a workload rollout: identify traffic classes, canary representative payloads, verify both directions, persist the setting correctly for the operating system, and retain the prior value for rollback. Do not lower every workload blindly when only one route is constrained.

Normal-state check: the configured Amazon VPC foundations control point, its dependency chain, and its return/response behavior must all agree. Production scenario: symptom, competing hypotheses, and decision

This result discriminates an MTU black hole from application authorization: the same credentials and TLS configuration succeed once packet sizing adapts.

Security, governance, scale, and failure boundaries

Permit only the ICMP and ICMPv6 control messages required for network correctness instead of treating all ICMP as inherently unsafe. PMTUD messages are part of the IP control plane; filtering them can create availability failures that resemble attacks or application defects. Scope rules to expected sources and destinations when the architecture allows, record network ACL and security-group changes, and monitor unexpected ICMP patterns. A lower MTU is not a confidentiality or authorization control. Keep TLS, workload identity, routing segmentation, security groups, network ACLs, and inspection policy independent. Stateful inspection appliances must pass the feedback signal in both directions and must not silently normalize packets in a way that invalidates evidence. Essence / mental model

A Client VPN session needs two independent approvals before a destination is usable: the endpoint route table must select a target network, and an authorization rule must grant the authenticated user or group access to that destination. A route is reachability intent, not permission. An authorization rule is permission, not a route. Network security groups, destination routes, and application authorization remain additional layers. Associating a target subnet adds the VPC route automatically, while peered VPCs, on-premises networks, and internet egress destinations require explicit routes. When multiple subnets are associated for resilience, AWS recommends identical routes for each association so a client does not receive a different reachability outcome based on the selected target network. With split tunnel enabled, routes are pushed to clients when the connection is established. Adding a route later does not retrofit the active client route table; AWS warns that resetting client connections can be required. Authorization follows longest-prefix matching, while a 0.0.0.0/0 rule is evaluated last and can be made group-specific to avoid unintentionally granting every user.

Architecture, dependencies, and normal flow

Define a destination matrix before configuration: destination CIDR, route target, associated subnet copies, authorized group, destination security policy, and application owner. Use at least two target-network associations in distinct Availability Zones when the endpoint needs resilience, then replicate every nonlocal destination route to each association. For on-premises access, the route target is the associated subnet, and the VPC path continues through Transit Gateway, virtual private gateway, or another designed attachment; return routing must include the Client VPN client CIDR. Authorization rules can grant all users or a specific directory group. Prefer specific prefixes and groups. Longest-prefix selection means a /24 rule is considered before a /16, and the all-networks 0.0.0.0/0 rule is evaluated last. A broad rule for one group does not become a general deny list for others; model grants explicitly. Under split tunnel, announce only required corporate routes to limit client route churn and avoid accidentally diverting unrelated internet traffic. Treat route changes as connection-affecting and schedule reconnection evidence in the rollout plan.

Essence / mental model

Cloud WAN route policies add ordered, declarative route selection to the core network policy. In policy version 2025.11, a route policy has conditions that identify routes and actions that decide how matching routes are handled. Conditions can reason about attributes such as prefix-list aliases, attachment labels, segments, and BGP communities. Actions can accept or reject routes, steer preference, or filter route exchange at core-network edges according to the documented schema. The essential mental model is that attachment placement and route acceptance are different decisions. An attachment policy decides where an attachment belongs; a route policy decides what advertised route information is accepted, preferred, shared, or rejected. Policy order matters because an earlier match can determine the outcome before a later general rule. Segment sharing creates potential reachability, but route policy still governs the routes exchanged. Labels and communities therefore become part of the routing control plane and must be managed with the same rigor as CIDRs and ASNs.

Architecture, dependencies, and normal flow

Start with explicit intent tables: producer attachment, segment, allowed prefixes, permitted receiving segments or edges, expected BGP community, preference, and default outcome. Define prefix-list aliases centrally so business ranges are reviewed once, but remember that changing an alias can affect every route policy that references it. Attachment labels should be immutable enough for policy; avoid free-form labels that application teams can alter without network review. Put narrow rejection or high-priority steering rules before broad acceptance rules and finish with a deliberate default. For multi-Region cores, decide whether routes should cross each edge and how failures change preference. Service insertion and shared-services patterns need symmetric return routing: a forward route steered through an inspection segment without a matching reverse decision creates stateful failure. Stage policy updates on a controlled core-network policy version, inspect proposed changes, and compare resulting route tables at each edge before execution. A syntactically valid JSON policy is not proof that the match set expresses the intended topology.

Essence / mental model

An S3 access point creates a named network and policy boundary for one bucket. A VPC-origin access point accepts requests only from the specified VPC, and that network origin is fixed when the access point is created. The access point has an ARN and a DNS alias; applications can address the access point instead of the bucket endpoint. The VPC restriction is enforced by S3, but the client still needs a path to S3, normally through an S3 gateway or interface endpoint according to the workload and DNS design. Authorization is layered. The caller identity policy, access-point policy, bucket policy, organization controls, and VPC endpoint policy can all participate. The bucket owner must delegate access-point authority in the bucket policy for access-point policies to grant access in the intended pattern. In same-account use, access-point and bucket policy evaluation differs from cross-account use, where both account boundaries must allow the request. A private network origin does not turn an implicit or explicit authorization deny into allow.

Architecture, dependencies, and normal flow

For a gateway endpoint, associate the required route tables and scope its policy. For interface endpoints, plan private DNS and cost.
