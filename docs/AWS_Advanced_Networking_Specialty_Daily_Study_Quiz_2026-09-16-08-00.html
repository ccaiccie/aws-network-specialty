Elastic network interface address mobility, source/destination checking, and zonal failover boundaries

Primary feature lesson sourceElastic network interfaceshttps://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-eni.html

Classification/platform: Official Amazon EC2 feature documentation. Source date: no update date displayed; checked 2026-09-16. Supports: Network-interface attributes, primary versus secondary interfaces, movable secondary IPv4 addresses, source/destination checks, requester-managed interfaces, and network-card constraints.

Scenario support sourceMultiple network interfaces for your Amazon EC2 instanceshttps://docs.aws.amazon.com/AWSEC2/latest/UserGuide/scenarios-enis.html

Classification/platform: Official Amazon EC2 architecture and implementation guidance. Source date: no update date displayed; checked 2026-09-16. Supports: Management-network separation, appliance interfaces, dual-homing constraints, and low-budget failover by moving an interface or secondary address.

Essence / mental model

An elastic network interface is a VPC object with an Availability Zone placement, subnet-derived addresses, security groups, a MAC address, and a source/destination-check flag. Those attributes follow the interface when a detachable secondary interface moves between instances in the same Availability Zone. The primary interface is different: it cannot be detached from its instance. A secondary private IPv4 address can also be reassigned independently, which is often a faster and narrower failover primitive than moving an entire interface. Source/destination checks are enabled by default because ordinary instances should originate or terminate their traffic; an instance acting as a router, NAT device, or firewall must have the check disabled. Address mobility preserves a network identity, but it does not preserve process state, sessions, neighbor caches, or cross-zone reachability.

Architecture, dependencies, and normal flow

Choose the movable object deliberately. Moving a secondary private IPv4 keeps the standby interface and operating-system configuration stable; moving a secondary interface also preserves its security groups, MAC address, and all assigned addresses. Both approaches remain constrained to the interface's Availability Zone because a network interface belongs to one subnet. For multi-AZ recovery, design a higher-level mechanism such as load balancing, DNS, or routing instead of assuming ENI portability. Attach management and data interfaces only when operating-system policy routing and reverse-path behavior are understood. A dual-homed application normally terminates traffic on each interface; it does not automatically route packets between subnets. For a middlebox, disable source/destination checking on every forwarding interface and provide explicit forward and return routes.

Production scenario: symptom, competing hypotheses, and decision

A stateful inspection appliance fails its application health check. Automation successfully detaches its data interface from instance A and attaches it to warm instance B, but traffic still blackholes. The interface is attached, its private address and security groups are present, and the standby process is running. Competing hypotheses include stale neighbor state, missing operating-system routes, source/destination checking, an asymmetric VPC route, and an interface attached to the wrong device index. The decisive observation is that B still has source/destination checking enabled, so EC2 rejects transit traffic even though the interface is healthy. The team disables the check on the forwarding interface, verifies policy routing and both route-table directions, then performs a bounded flow test before returning the appliance to service.

Security, governance, scale, and failure boundaries

Classification/platform: Official AWS Site-to-Site VPN troubleshooting flow. Source date: no update date displayed; checked 2026-09-16. Supports: The ordered IKE, IPsec, tunnel-IP, and BGP validation sequence for a customer gateway using dynamic routing.

Essence / mental model

Site-to-Site VPN logs turn the tunnel from a single UP or DOWN indicator into a sequence of protocol evidence. Tunnel activity records expose IKE phase 1, IKE phase 2, NAT traversal, dead-peer detection, and detailed negotiation messages. BGP records expose session transitions, prefix-limit events, OPEN attributes, and whether a route was advertised, updated, withdrawn, or denied. The log stream is keyed by VPN connection and outside tunnel IP, which matters because each connection has two independent tunnels. The correct diagnostic model is layered: IKE must establish keying, IPsec must establish the protected data channel, tunnel inside addresses must pass traffic, and BGP must form and exchange usable routes. A later-layer failure should not be treated as proof that the earlier layer is down.

Architecture, dependencies, and normal flow

Enable logs for both tunnels and choose a CloudWatch Logs group whose resource policy can scale. AWS documents a 5,120-character resource-policy limit and recommends an /aws/vendedlogs/ prefix to reduce policy growth pressure. Grant only the log-delivery permissions needed by the principal configuring the feature. Normalize fields such as resource ID, outside IP, IKE states, BGP event type, status, prefix, AS path, MED, and next hop into dashboards without discarding the original message. Retain enough history to correlate maintenance, rekeys, internet-path instability, and customer-device changes. Build alarms on sustained protocol transitions and prefix-limit events rather than every normal rekey. Preserve the two-tunnel distinction so one noisy peer does not mask loss of redundancy.

Classification/platform: Official Amazon EC2 operational API reference. Source date: no update date displayed; checked 2026-09-16. Supports: Inventory and state inspection of route-table announcements with IDs, filters, pagination, and announcement objects.

Essence / mental model

A Transit Gateway route table announcement is a control-plane object that advertises a specific Transit Gateway route table through a specific peering attachment. The create request therefore binds two distinct identifiers: the local route table whose reachability is being announced and the peering attachment across which it is shared. The returned announcement object and its lifecycle state are the evidence that the advertisement object exists. This is not the same as associating an ingress attachment with a route table, enabling propagation into a table, or adding a static route. An announcement can expose a route-table domain to its peer, but it does not by itself prove that a source attachment consults that table, that the peer accepted usable reachability, or that return routes and policy are symmetric.

Architecture, dependencies, and normal flow

Treat each announcement as an explicit inter-domain contract. Record the owning account, Transit Gateway, route table, peering attachment, peer, intended prefix set, direction, change ticket, and rollback owner. Use DryRun before creation to separate IAM authorization from object-state errors. Tag the announcement where supported so an inventory can reconcile it with the intended topology. Do not advertise a broad table merely because the peering is available; first review every propagated and static route in that table and understand which routes may change dynamically. Pair the remote import behavior with local attachment association and propagation diagrams. For high availability, validate both the peering data path and the route-domain design rather than creating duplicate announcements without ownership.

Essence / mental model

A confidence threshold controls sensitivity: high confidence minimizes false positives, medium balances detection and disruption, and low maximizes visibility but needs more tuning. Each rule then chooses ALERT or BLOCK. This creates two independent decisions—what the detector believes and what the policy does. The control applies to DNS queries processed by Route 53 Resolver for associated VPCs. It is an early network-security checkpoint, but it does not inspect an already-known IP connection, validate application identity, or replace egress controls.

Architecture, dependencies, and normal flow

Essence / mental model

An EKS cluster chooses IPv4 or IPv6 at creation and cannot change that family later. In IPv6 mode, Pods and Kubernetes services receive IPv6 addresses rather than dual-stack addresses. Worker nodes still have IPv4 and IPv6, and the VPC and subnets retain both families because VPC operation and legacy dependencies still require IPv4. VPC CNI uses IPv6 prefix delegation on supported Nitro instances, avoiding per-Pod IPv4 scarcity. For an IPv6 Pod reaching an external IPv4 endpoint, a chained host-local plugin supplies a node-local IPv4 address that the VPC CNI source-translates to the node primary IPv4. This built-in compatibility path differs from generic subnet DNS64 and NAT64, and EKS guidance warns that enabling DNS64 can unexpectedly redirect such traffic.

Architecture, dependencies, and normal flow

Create a new IPv6-family cluster in a VPC whose selected subnets have IPv4 and IPv6 CIDRs, auto-assign IPv6 for nodes, IPv6 routes, and IPv6-aware security controls. Use a supported recent VPC CNI, configure IPv6 and prefix delegation, and assign the recommended IPv6 IAM policy to the CNI role. Choose Nitro-based EC2 nodes or supported Fargate behavior, and account for unsupported Windows, Outposts, FSx for Lustre, and custom networking combinations documented for the feature. For ingress, use a current AWS Load Balancer Controller with dualstack load balancers and IP targets for IPv6 Pods. Evaluate every add-on and downstream AWS or on-premises dependency. Do not assume the enormous /80 Pod prefix removes CPU, memory, ENI, or Fargate subnet constraints.
