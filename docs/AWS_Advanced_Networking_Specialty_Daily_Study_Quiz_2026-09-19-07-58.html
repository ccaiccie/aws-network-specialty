Replacing a VPC local route target with an appliance ENI: per-CIDR steering, recovery, and source/destination-check dependencies

Primary feature lesson sourceReplace or restore the target for a local route - Amazon Virtual Private Cloudhttps://docs.aws.amazon.com/vpc/latest/userguide/replace-local-route-target.html

Classification/platform: Official Amazon VPC feature and configuration documentation. Source date: no update date displayed; checked 2026-09-19. Supports: The supported replacement of a local route target with a network interface or gateway-load-balancer endpoint, eligible destination CIDRs, and restoration to the local target.

Scenario support sourcereplace-route — AWS CLI Command Referencehttps://docs.aws.amazon.com/cli/latest/reference/ec2/replace-route.html

Classification/platform: Official AWS CLI implementation reference. Source date: no update date displayed; checked 2026-09-19. Supports: Exact route replacement syntax, destination matching, mutually exclusive target parameters, local-target restoration, dry-run behavior, and error boundaries.

Essence / mental model

Every VPC route table contains local routes for the VPC CIDR blocks, but AWS lets an eligible local route target be replaced so traffic matching that exact VPC CIDR is steered through a network appliance interface or a Gateway Load Balancer endpoint. The route remains a destination-prefix decision: replacing the target for one associated CIDR does not rewrite every local route or turn the appliance into a universal next hop. Restoration is explicit—the same route can be returned to the local target. This capability is therefore best understood as surgical east-west service insertion, with the route table, selected appliance target, and symmetric return design all treated as one controlled change.

Architecture, dependencies, and normal flow

Choose the route table and destination CIDR deliberately. The destination supplied to ReplaceRoute must exactly match an existing route; it is not a request to create a more-specific route. Confirm that the target network interface belongs to an appliance that can forward the intended packets and that source/destination checking is disabled where the appliance role requires it. Then model both directions. A forward-path route that sends only one side through a stateful appliance can break established sessions even while the route is active. Use separate route tables, high-availability appliance placement, and documented failure handling rather than assuming an ENI target automatically fails over to a peer.

Normal-state check: the configured Amazon VPC foundations control point, its dependency chain, and its return/response behavior must all agree. Essence / mental model

A Site-to-Site VPN customer gateway resource represents the on-premises or third-party VPN device, but AWS can identify that device with a private certificate issued through AWS Private CA instead of relying only on a fixed public outside IP. For a public VPN using certificate authentication, the customer-gateway IP field can be omitted. The certificate is an identity input to IKE authentication; it does not replace tunnel routing, BGP, NAT traversal, or the two-tunnel resilience model. Use a subordinate private CA for this pattern and manage the certificate lifecycle as carefully as the network device itself.

Architecture, dependencies, and normal flow

Decide first whether the VPN is public or private and whether the attachment target is a virtual private gateway, transit gateway, or Cloud WAN. Select a supported BGP ASN and avoid conflicts with the AWS-side ASN. When the device is behind NAT, its configured public address and UDP 500/4500 reachability remain operational dependencies even if certificate identity is used. IPv6 customer-gateway addressing has attachment limitations and must be checked against the selected service. Provision the private certificate, create the customer-gateway object with CertificateArn, create the VPN connection, configure both downloaded tunnel profiles, and test renewal before the initial certificate approaches expiry.

Essence / mental model

A Route 53 alias record maps a name to an eligible AWS resource or another record while remaining a Route 53 record type such as A or AAAA. Unlike a CNAME, an alias can exist at the zone apex because it does not replace the apex with a CNAME record. Record type still matters: the alias and target must be compatible with the query type. TTL behavior belongs to the target. An alias to an AWS resource uses that resource’s default response TTL, while an alias to another record inherits the target record’s TTL. This makes the alias a routing indirection, not an independent TTL wrapper.

Architecture, dependencies, and normal flow

For an Application or Classic Load Balancer, create A and—when IPv6 is required—AAAA alias records against the load balancer DNS name. In a different account, Route 53 might not enumerate the target, so enter the DNS name explicitly and use the documented dualstack form where required. Decide whether Evaluate Target Health should use the target’s health behavior and understand how empty or unhealthy target groups affect answers. Alias queries to supported AWS resources do not incur the same Route 53 query charge as ordinary records, but the target service still has its own cost and availability model.

Next discriminating check: test the next unverified layer—route or resolver selection, policy decision, target/service state, then application behavior—without broadening access prematurely.

Security, governance, scale, and failure boundaries

Prefer private endpoints and least-privilege bucket, endpoint, IAM, and security-group policies. Enhanced VPC routing increases network control and evidence, but it does not replace Redshift database authorization or S3 object permissions. Avoid a broad NAT route as the first repair for a missing service endpoint. Protect private DNS and endpoint policy changes, encrypt data in transit and at rest, and monitor rejected flows. If cross-Region S3 is required, review data-residency and egress implications. Treat cluster restart and authentication endpoint availability as part of the production threat and resilience model.

For high availability, use the feature’s documented multi-AZ/Region or multi-path capabilities where applicable, maintain an intentional rollback, and record account ownership. Revisit quotas, supported IP families, protocol/platform version constraints, and cost/scale implications in the cited AWS documentation before production expansion.
