1. Capacity before CIDR: operating VPC Network Address Usage as a design signal

Primary feature/configuration source
CloudWatch metrics for your VPCs
https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cloudwatch.html
Official AWS service documentation · Living documentation; accessed 2026-09-14
Separate scenario/evidence source
Designing hyperscale Amazon VPC networks
https://aws.amazon.com/blogs/networking-and-content-delivery/designing-hyperscale-amazon-vpc-networks/
Official AWS technical blog · Published 2022-10-04

Essence

Network Address Usage is a VPC-scale resource-counting signal, not a count of free subnet addresses. Enable it per VPC, alarm on its slow daily series, and model both the VPC-local and peered-domain values before a quota boundary prevents new networked resources.

Architecture, dependencies, and normal flow

  • Amazon VPC calculates NAU units from network-address-consuming resources and publishes NetworkAddressUsage in AWS/EC2 with a per-VPC dimension.
  • NetworkAddressUsagePeered expands the accounting view across peered VPCs; a locally modest VPC can therefore participate in a large aggregate domain.
  • Equivalent ResourceCount series in AWS/Usage support service-quota style dashboards, while the AWS/EC2 series is convenient for per-VPC alarms.
  • The documented reporting interval is every 24 hours, so the metric is a capacity-planning signal rather than a real-time incident detector.
  • Exhausting NAU or peered NAU can block creation of EC2 instances, Network Load Balancers, VPC endpoints, Lambda networking, transit attachments, and NAT gateways even when a subnet appears to have free addresses.

Configuration hierarchy and safe workflow

  1. Inventory VPCs and their peering relationships before selecting alarm scope.
  2. Enable NAU monitoring on every VPC whose growth must be forecast; an absent series can simply mean monitoring is disabled.
  3. Graph local and peered values against the applicable quota, preserve 30- and 90-day slopes, and attach ownership metadata.
  4. Use a warning threshold for lead time, not the quota itself; reconcile step changes to deployments and account onboarding.
  5. When a create API fails, compare NAU, subnet AvailableIpAddressCount, service quotas, and the failing API error instead of assuming CIDR exhaustion.
Operator checks
  • Enable the VPC attribute for network-address-usage metrics before expecting data.
  • Query AWS/EC2 NetworkAddressUsage and NetworkAddressUsagePeered with the VPC dimension.
  • Correlate CloudTrail create failures, Service Quotas, and subnet AvailableIpAddressCount.

Production scenario

Topology
A platform account hosts shared endpoints and load balancers; six application VPCs are fully peered for a migration interval.
Symptom
A new interface endpoint and then an NLB fail to provision although the chosen subnets still report free IPv4 addresses.
Healthy evidence
Route tables, DHCP, and existing flows remain healthy; only new resources fail.
Competing hypotheses
  • the target subnet is out of addresses
  • the VPC or its peered domain reached an NAU quota
  • IAM denies the create calls
  • a Region-specific service quota is lower than the design assumption
Discriminating sequence
Read the exact create-event error, inspect both NAU series and their timestamps, query subnet address availability, and compare current usage with Service Quotas.
Root cause
The peered-domain NAU boundary was reached; free addresses in one subnet did not disprove the VPC-wide capacity limit.
Bounded remediation
Remove obsolete endpoints and peering links, scale out the topology where appropriate, request the justified quota increase, and alarm on forecasted exhaustion.
Verification
After capacity is restored, create a canary endpoint in a test subnet, confirm its lifecycle, and annotate the next 24-hour NAU sample.

Evidence ladder

Observed bundle: NetworkAddressUsage is below the local warning line; NetworkAddressUsagePeered crosses it after a peering change; the failed CreateVpcEndpoint event cites capacity.

What this proves: The failure correlates with the peered accounting domain and the create operation, not merely with a packet path.

What this does not prove: A daily aggregate cannot identify the exact consuming resource or prove which deployment caused the jump.

Next discriminating check: List recent ENI-producing resources and create events, then reconcile the delta against the next published sample.

2. Fast failure detection is layered: Direct Connect BFD does not supervise the overlay

Primary feature/configuration source
AWS Direct Connect connection options
https://docs.aws.amazon.com/directconnect/latest/UserGuide/connection_options.html
Official AWS service documentation · Living documentation; accessed 2026-09-14
Separate scenario/evidence source
Best practices to optimize failover times for overlay tunnels on AWS Direct Connect
https://aws.amazon.com/blogs/networking-and-content-delivery/best-practices-to-optimize-failover-times-for-overlay-tunnels-on-aws-direct-connect/
Official AWS technical blog · Published 2025-08-21

Essence

Asynchronous BFD on a Direct Connect virtual interface detects underlay forwarding failure quickly after the customer router is configured, but it cannot prove that an IPsec or GRE overlay headend is alive. Engineer and test detection at every layer that can fail.

Architecture, dependencies, and normal flow

  • AWS automatically enables asynchronous BFD on each Direct Connect virtual interface, but it becomes effective only when the customer router is configured for the BGP neighbor.
  • The BFD session follows the virtual-interface underlay peer and can withdraw BGP reachability when that adjacency fails.
  • An overlay tunnel can terminate beyond a healthy Direct Connect router; its headend, security policy, or tunnel process can fail while underlay BFD remains Up.
  • Overlay BGP timers, tunnel keepalives, and application health each cover different failure boundaries.
  • Aggressive timers improve detection only within their monitored layer and can amplify transient loss, CPU pressure, or asymmetric paths into unnecessary churn.

Configuration hierarchy and safe workflow

  1. Draw the physical connection, VIF BGP peer, tunnel endpoints, overlay BGP peer, and application dependency as separate failure domains.
  2. Confirm BFD negotiation and counters at both ends rather than assuming the AWS default alone activates detection.
  3. Set timers from measured loss and convergence objectives, then validate provider and router support.
  4. Inject an underlay failure, an overlay-headend failure, and an application failure separately.
  5. Measure detection, route withdrawal, alternate-path installation, session reset behavior, and application recovery.
Operator checks
  • Show BFD neighbors and counters on the customer router.
  • Inspect Direct Connect VIF and BGP state alongside tunnel and overlay-route telemetry.
  • Run controlled failure tests with timestamped probes on both redundant paths.

Production scenario

Topology
Two private VIFs terminate on separate routers; encrypted overlays terminate on firewalls behind those routers and advertise application prefixes with overlay BGP.
Symptom
When one firewall process is stopped, traffic blackholes for the full overlay BGP hold time although VIF BFD stays Up.
Healthy evidence
The fiber, VLAN, VIF peer, and AWS-side BFD adjacency are healthy.
Competing hypotheses
  • Direct Connect underlay loss
  • customer router control-plane failure
  • overlay tunnel headend failure
  • an application-only health failure
Discriminating sequence
Compare BFD state, VIF BGP state, tunnel security associations, overlay BGP timers, and a probe sourced through each path.
Root cause
The overlay headend failed outside the failure boundary supervised by VIF BFD.
Bounded remediation
Add supported overlay liveness and carefully tuned overlay BGP timers, prefer independent termination domains, and avoid timers below demonstrated stability.
Verification
Repeat all three failure injections and record route-withdrawal and end-to-end recovery times.

Evidence ladder

Observed bundle: VIF BFD Up; underlay BGP Established; IPsec keepalive Down; overlay prefix remains until the configured hold timer; alternate path accepts the prefix.

What this proves: The physical/VIF underlay is not the failed layer and delayed withdrawal is controlled by overlay convergence.

What this does not prove: It does not prove the application is healthy after the overlay recovers or that timers are safe during congestion.

Next discriminating check: Probe the overlay endpoint directly and inspect tunnel and overlay-BGP event timestamps.

3. Make Transit Gateway charge ownership deterministic with first-match metering

Primary feature/configuration source
Flexible cost allocation
https://docs.aws.amazon.com/vpc/latest/tgw/metering-policy.html
Official AWS service documentation · Living documentation; accessed 2026-09-14
Separate scenario/evidence source
Introducing Flexible Cost Allocation for AWS Transit Gateway
https://aws.amazon.com/blogs/networking-and-content-delivery/introducing-flexible-cost-allocation-for-aws-transit-gateway/
Official AWS technical blog · Published 2025-11-21

Essence

Flexible Cost Allocation changes who is billed for qualifying Transit Gateway flows without changing packet routing. Its ordered, first-match policy needs the same rigor as an ACL: specific exceptions first, broad defaults last, and cost evidence after propagation.

Architecture, dependencies, and normal flow

  • A metering policy is associated with a Transit Gateway and evaluates each flow against rules in ascending numerical order.
  • The first matching entry chooses the metered owner: source attachment owner, destination attachment owner, or Transit Gateway owner.
  • Rules can match attachment type or ID and, where appropriate, flow attributes such as source or destination CIDR, ports, and protocol.
  • A middlebox attachment can be declared so inspection transit does not incorrectly become the economic source or destination.
  • The capability allocates Transit Gateway processing and supported transfer charges; it does not install routes, change reachability, or steer inspection.

Configuration hierarchy and safe workflow

  1. Write the desired chargeback matrix before creating rules.
  2. Number specific exceptions with gaps, then add broader attachment-class rules and a documented default.
  3. Model both directions because a return flow has reversed source and destination properties.
  4. Declare the inspection attachment as a middlebox when that reflects the traffic chain.
  5. Validate with tagged test flows and Cost Explorer or billing exports after the documented billing delay.
Operator checks
  • List the policy entries in ascending rule order.
  • Record source and destination attachment IDs and the 5-tuple for a bounded test.
  • Use cost evidence after propagation to verify the metered account.

Production scenario

Topology
A central Transit Gateway connects Direct Connect, finance and marketing VPCs, a partner VPC, and a shared inspection VPC.
Symptom
Finance expected receiver-pay for on-premises ingress, but central networking receives the processing charge for one traffic class.
Healthy evidence
Transit routes, appliance symmetry, and application sessions are correct.
Competing hypotheses
  • routing selected the wrong attachment
  • the broad metering rule shadowed the specific exception
  • the inspection VPC was not declared as middlebox
  • billing evidence has not propagated yet
Discriminating sequence
Replay the flow tuple through policy rules in numerical order, examine middlebox registration, then compare a known test interval after billing data is available.
Root cause
A low-number broad rule matched first, so the specific receiver-pay rule was unreachable.
Bounded remediation
Insert the narrow finance exception at a lower rule number, retain gaps, document the default, and review the reverse direction.
Verification
Generate tagged test traffic and confirm the expected metered account in cost evidence without any route-table change.

Evidence ladder

Observed bundle: Flow logs show DX attachment to finance; metering entries show rule 50 broad DX match before rule 100 finance match; cost data lands on central IT.

What this proves: The packet path is correct and the first-match economic rule selected the undesired owner.

What this does not prove: It does not prove an invoice defect or a routing problem, and very recent traffic may not yet appear.

Next discriminating check: Evaluate the exact tuple against each rule and rerun a bounded test after policy propagation.

4. Route 53 multivalue answers: health-aware DNS diversity, not a load balancer

Essence

Multivalue answer routing can return up to eight healthy records and vary the set across resolver queries. It improves DNS-level availability, but resolver caching, record health configuration, and the all-unhealthy fallback define its real behavior.

Architecture, dependencies, and normal flow

  • Create multiple records with the same name and type, select multivalue answer, and optionally associate health checks.
  • Route 53 can return up to eight healthy records in one response; recursive resolvers and clients decide how those addresses are attempted.
  • Records without health checks are treated as healthy, so one unchecked address can remain eligible while checked peers are removed.
  • When all records are unhealthy, Route 53 can still return records rather than an empty answer, favoring possible reachability over certain DNS failure.
  • This policy is not a substitute for a load balancer: it has no connection awareness, no per-request scheduling, and cannot recall an address already cached at a resolver.

Configuration hierarchy and safe workflow

  1. Define one endpoint per record and give each endpoint a health signal that tests the dependency the client needs.
  2. Choose TTL from recovery objectives while respecting query volume and resolver behavior.
  3. Test mixed healthy/unhealthy sets, unchecked records, and the all-unhealthy condition.
  4. Capture authoritative answers and recursive-resolver answers separately.
  5. Use endpoint telemetry to verify whether clients retry alternate addresses.
Operator checks
  • Query authoritative Route 53 name servers and a recursive resolver with TTL display.
  • List record health-check associations and health-check status.
  • Correlate endpoint logs with the address set cached by the client resolver.

Symptom

Healthy evidence

Competing hypotheses

Query the authoritative name servers, inspect record-to-health-check associations, compare resolver cache age and TTL, and test all-health states in a controlled zone.
Root cause
A cached old answer and one unchecked record explain continued attempts; Route 53 cannot revoke cached DNS data.
Bounded remediation
Associate health checks with every intended endpoint, align TTL with recovery goals, and use client or load-balancer retries where connection-aware failover is required.
Verification
After TTL expiry, query multiple resolvers and prove the failed endpoint is absent until its health check recovers.

What this does not prove: It does not prove every resolver honors TTL precisely or that clients retry a second address.

5. DynamoDB gateway endpoints: route ownership and authorization must both agree

Primary feature/configuration source

Essence

A DynamoDB gateway endpoint keeps same-Region service traffic on AWS networking by inserting a service prefix-list route into selected route tables. Reachability succeeds only when route association, Region, DNS destination, IAM, resource policy, and endpoint policy align.

Architecture, dependencies, and normal flow

  • The gateway endpoint is associated with selected VPC route tables; AWS adds a route whose destination is the DynamoDB managed prefix list and whose target is the endpoint.
  • Gateway endpoints do not place endpoint ENIs in subnets and do not use endpoint security groups; route-table association is the network control.
  • The route is Regional and serves the Region's DynamoDB endpoint; cross-Region requests do not inherit that private route merely because a local endpoint exists.
  • The endpoint policy is a resource-based control on use of the endpoint and is evaluated with identity and applicable DynamoDB resource policies.
  • Conditions such as aws:sourceVpce can deliberately restrict data-plane access but can also block paths such as consoles or workloads that do not traverse that endpoint.

Configuration hierarchy and safe workflow

  1. Create the endpoint for the intended Region and associate every workload route table that should use it.
  2. Inspect the AWS-managed prefix-list route after association and preserve more-specific custom-route intent.
  3. Start with a bounded endpoint policy and prove identity authorization separately.
  4. Resolve and connect to the correct Regional DynamoDB hostname from each subnet.
  5. Use CloudTrail data events and policy simulation to distinguish routing from authorization.
Operator checks
  • Describe the endpoint, service name, policy, and associated route-table IDs.
  • Inspect effective routes for the DynamoDB managed prefix list.
  • Issue a signed DynamoDB request and correlate its CloudTrail authorization context.

Verification

What this does not prove: A route does not prove TLS/DNS correctness, and an AccessDenied does not prove network reachability for another subnet.

Boundary model: Control-plane boundary. Request-side modification renames the ALB-generated TLS and mutual-TLS metadata headers before they reach the target. That distinction governs the first diagnostic move: Inventory existing target, proxy, and CDN header ownership before enabling attributes. Healthy path: Normal flow and dependencies. An empty attribute value means no modification, so drift can silently restore target-provided behavior. This prevents a console screenshot of one object from being mistaken for the complete effective configuration.

Essence

Architecture, dependencies, and normal flow

  • CloudFront can allocate an account-dedicated Anycast list spread across geographic areas and associate it with one or more distributions.
  • AWS documents a 21-address allowlisting use case and a separate three-address apex-domain routing use case; choose the product shape that matches the requirement.
  • Distributions using an Anycast list must use all edge locations, and an IPv4-only list is incompatible with an IPv6-enabled distribution.
  • Custom connection groups provide a routing endpoint and configuration boundary for distributions that share connection behavior.
  • Viewer DNS must point to the correct routing endpoint or static addresses for the selected model; an association alone cannot redirect a name that still resolves to an old group.

Configuration hierarchy and safe workflow

  1. Classify the requirement as provider allowlisting or apex routing and request the corresponding allocation.
  2. Select IPv4 or dual-stack from actual client reachability and distribution settings.
  3. Enable connection groups, associate a test distribution, and capture the new routing endpoint.
  4. Lower DNS TTL before cutover, validate certificates and aliases, then change DNS in a staged cohort.
  5. Monitor both address families, keep rollback records, and raise TTL only after the old cache window expires.
Operator checks

  • Inspect connection-group routing endpoints and distribution price class.

8. Interpret WAF CAPTCHA and Challenge as token-state machines

Primary feature/configuration source
How AWS WAF CAPTCHA and Challenge actions work
https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge.html
Official AWS service documentation · Living documentation; accessed 2026-09-14
Separate scenario/evidence source
CAPTCHA and Challenge logs and metrics
https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge-logs-metrics.html
Official AWS service documentation · Living documentation; accessed 2026-09-14

Essence

CAPTCHA and Challenge actions do not simply block or allow. They evaluate an encrypted client token, its domain and immunity time, then either terminate with a puzzle/challenge or continue rule evaluation. Logs and labels expose the branch taken.

Architecture, dependencies, and normal flow

  • A Challenge action presents a generally silent browser challenge; CAPTCHA can require an interactive puzzle when no valid token satisfies the rule.
  • If the request carries a valid, unexpired token for the protected domain and configured immunity window, the action is nonterminating and evaluation continues.
  • When a token is missing, invalid, domain-mismatched, or expired, the action terminates that request with the appropriate challenge behavior.
  • Token domains and JavaScript integration matter for applications spanning hostnames; cookies and browser execution are part of the data path.
  • WAF logs, labels, and action metrics distinguish challenge issuance, successful token reuse, and rejection causes better than aggregate blocked-request counts.

Configuration hierarchy and safe workflow

  1. Map every protected hostname and the pages or APIs that can execute challenge integration.
  2. Set web-ACL and rule-level immunity times from user-session risk, not convenience alone.
  3. Enable logging with redaction appropriate for privacy and preserve token labels and terminating-rule fields.
  4. Test no-token, valid-token, expired-token, domain-mismatch, and nonbrowser clients.
  5. Correlate WAF action with browser developer tools, cookie scope, and origin access logs.
Operator checks
  • Inspect WAF logs for action, terminatingRuleId, labels, and token rejection reason.
  • Compare web-ACL token domains with browser cookie domain and request host.
  • Replay with a clean session, a valid token, and an intentionally expired token.

Production scenario

Topology
A CloudFront distribution serves app.example.com and api.example.com under one web ACL; a Challenge rule protects login and a CAPTCHA rule protects account recovery.
Symptom
Users pass the challenge on the app host but receive repeated challenges on the API host; bot dashboards show a sudden rise in challenged requests without a matching origin error rise.
Healthy evidence
CloudFront, origin health, and the rule priority are stable.
Competing hypotheses
  • the origin login service is failing
  • immunity time is shorter than the user flow
  • token domain configuration excludes api.example.com
  • a higher-priority terminating rule blocks before token evaluation
Discriminating sequence
Inspect the exact WAF log action and labels, token-domain settings, cookie attributes, rule priority, and timestamps across both hosts.
Root cause
The token cookie is not valid for the API hostname, so every API request enters the challenge branch.
Bounded remediation
Configure approved token domains and integration scope, preserve least privilege, and retest expiry and cross-host flows.
Verification
Use a fresh browser session to obtain a token, call both hosts within and after immunity, and confirm nonterminating labels followed by intentional expiry behavior.

Evidence ladder

Observed bundle: app request: token valid and rule nonterminating; API request: token rejected for domain mismatch and Challenge terminates; origin has no corresponding 5xx.

What this proves: The failure is at WAF token validation before origin processing.

What this does not prove: A valid token does not prove the user is authorized by the application or benign.

Next discriminating check: Compare token cookie scope and WAF token-domain configuration for the exact host, then replay before expiry.

Essence

Architecture, dependencies, and normal flow

  • Flow logs are configured for an accelerator and delivered to a selected S3 bucket and prefix.
  • Records include the client and accelerator addresses and ports, endpoint details, protocol, packets, bytes, timestamps, action or log status, direction, and Region fields.
  • Version 2 includes VPC ID for applicable client-IP-preserving paths, improving endpoint attribution.
  • AWS documents capture windows up to about a minute, files published at roughly five-minute intervals, typical delivery within an hour, and possible delivery as late as 24 hours; a four-hour wait is a practical reliability boundary in the documentation.
  • Global Accelerator management and CloudWatch views use us-west-2 conventions even when endpoints serve other Regions, which can confuse responders searching only the endpoint Region.

Configuration hierarchy and safe workflow

  3. For an incident, define client IP, accelerator IP, port, protocol, and an expanded UTC time window.
  4. Query direction and reject or status fields, then join with endpoint, load-balancer, and application logs.
  5. Mark evidence incomplete until the delivery window has elapsed; distinguish no traffic from no file.
Operator checks
  • Describe accelerator flow-log settings and S3 destination policy.
  • Query S3 objects over a widened UTC window and parse the documented record version.
  • Join client tuple and endpoint fields with ALB and application logs.

11. CloudFormation stack refactoring moves ownership only when the plan is mutation-free

Primary feature/configuration source

Essence

Stack refactoring can move supported physical resources between stacks or rename logical IDs without replacement. The safety condition is strict: templates express only ownership reorganization, mappings are previewed, and ineligible or mutated resources stop the plan.

Architecture, dependencies, and normal flow

  • A refactor compares current stacks with proposed stack definitions and produces a preview of resource mappings and stack actions.
  • The physical resource and its operating state are preserved when the resource is eligible and its properties are not being changed.
  • Refactoring supports splitting, combining, and logical-ID changes, but is not a shortcut for a create, delete, or configuration update in the same operation.
  • CLI operations have documented stack-count and eligibility constraints; supported resources must meet the FULLY_MUTABLE requirement and several resource types remain unsupported.
  • Cross-stack references, exports, imports, nested-stack boundaries, stack policies, and destination templates must be evaluated before execution.

Configuration hierarchy and safe workflow

  1. Export current templates, inventory physical IDs, dependencies, exports, policies, drift, and resource eligibility.
  2. Prepare source and destination templates that preserve every resource property while changing only ownership or logical mapping.
  3. Create the refactor, wait for CREATE_COMPLETE, and review every mapping and action before execution.
  4. Block execution if the preview contains an unexpected create, delete, replacement, or property change.
  5. Execute in a controlled window, fetch both stack templates and physical IDs, then run drift and application checks.
Operator checks
  • Create the refactor from source and destination stack definitions.
  • Describe the refactor until preview status is complete, then inspect every action and mapping.
  • After execution, compare physical IDs, templates, outputs, drift, and network canaries.

Production scenario

Topology
A network monolith contains VPC, subnets, security groups, flow-log delivery, and shared IAM resources; the team wants separate network-core and observability stacks.
Symptom
The preview refuses one mapping and proposes an unexpected action for a Route 53 RecordSet included in the move.
Healthy evidence
Supported security groups and log resources map to their original physical IDs.
Competing hypotheses
  • CloudFormation cannot refactor any network resource
  • one resource type is unsupported
  • a property change converted reorganization into mutation
  • cross-stack outputs are unresolved
Discriminating sequence
Compare template properties byte-for-byte, inspect eligibility and preview actions, resolve exports/imports, and verify physical IDs.
Root cause
The plan combines an unsupported resource and a configuration change with an ownership move, violating refactor constraints.
Bounded remediation
Remove the unsupported resource from this refactor, stage its migration separately, preserve properties, and recreate the preview.
Verification
Require mapping-only actions, execute, then prove physical IDs, configuration, traffic, and stack drift are unchanged.

Evidence ladder

Observed bundle: Preview maps supported resources to unchanged physical IDs, flags RecordSet eligibility, and shows a property delta in the proposed destination.

What this proves: The blocker is resource eligibility and plan mutation rather than runtime dependency failure.

What this does not prove: A clean preview cannot prove application health or eliminate rollback planning.

Next discriminating check: Regenerate from property-identical templates and compare the resulting mappings and action types.

Service Connect creates a managed proxy in each participating task and a Cloud Map-backed logical namespace. Short-name discovery works only when deployment configuration, named port mappings, proxy resources, namespaces, and security-group paths form one consistent contract.

Architecture, dependencies, and normal flow

  • A client task connects to a local Service Connect proxy by endpoint name and port; that proxy selects a server task and connects to the server-side proxy.
  • The task definition names the relevant port mapping and can declare appProtocol; the ECS service maps that portName to a discovery name and client aliases.
  • A Cloud Map namespace is the logical grouping, must be in the same Region, and can span clusters or be shared across accounts with AWS RAM.
  • Client services can call endpoints in their namespace; client-server services also publish endpoints. Outside or nonparticipating applications cannot resolve Service Connect short names without another method.
  • Service updates create deployments that inject or reconfigure the proxy; security groups and VPC routes still govern the task-to-task data path.

Configuration hierarchy and safe workflow

  1. Name task-definition port mappings and verify the application actually listens on that container port and protocol.
  2. Set a cluster default or explicit service namespace, ensuring discovery names are unique.
  3. Allocate CPU and memory headroom for the proxy and create execution-role/log-group dependencies.
  4. Authorize security-group traffic between task ENIs on the Service Connect port and validate return routing.
  5. Deploy client-server before dependent clients, then test short name, proxy logs, CloudWatch metrics, and direct application health.
Operator checks
  • Describe ECS services, active deployments, and serviceConnectConfiguration.
  • Inspect task-definition named portMappings and appProtocol.
  • Query proxy logs and CloudWatch Service Connect metrics while testing short-name and direct-task paths.

Symptom

Healthy evidence
Cloud Map namespace, subnet routes, and the application on container port 8080 are healthy.

  • security groups block the proxy port
  • portName contract drift prevented proxy configuration
  • the application itself is down

Describe the active task definition and service deployment, compare portName/discoveryName/clientAlias, inspect proxy logs, then test the task IP and proxy path separately.

The service deployment references a port name no longer present in the task definition, so the injected proxy cannot expose the intended endpoint.

Deep engineering interpretation

Boundary model: Control-plane boundary. A client task connects to a local Service Connect proxy by endpoint name and port; that proxy selects a server task and connects to the server-side proxy. The task definition names the relevant port mapping and can declare appProtocol; the ECS service maps that portName to a discovery name and client aliases. That distinction governs the first diagnostic move: Name task-definition port mappings and verify the application actually listens on that container port and protocol. The engineer should write down the owner of each configuration object, the place where it is evaluated, and the delay between a change and observable evidence. Service Connect interconnects participating ECS services; it is not general VPC DNS for arbitrary clients. A passing check at a neighboring layer is useful negative evidence, but it is not permission to skip the component that owns the decision.

Healthy path: Normal flow and dependencies. A Cloud Map namespace is the logical grouping, must be in the same Region, and can span clusters or be shared across accounts with AWS RAM. Client services can call endpoints in their namespace; client-server services also publish endpoints. Outside or nonparticipating applications cannot resolve Service Connect short names without another method. Trace a healthy transaction from producer to consumer and label every name lookup, route or selection, policy evaluation, stateful hop, and telemetry export. For this design the practical next step is to set a cluster default or explicit service namespace, ensuring discovery names are unique. Record the expected input and output at each hop so that an incident can compare observed state with a known-good path instead of relying on a generic service health indicator.

Effective configuration: Configuration hierarchy. Allocate CPU and memory headroom for the proxy and create execution-role/log-group dependencies. The hierarchy must be reviewed from the broadest scope down to the most specific object, while ordered policies are read in their documented evaluation direction. Service updates create deployments that inject or reconfigure the proxy; security groups and VPC routes still govern the task-to-task data path. Configuration review should include defaults and empty values, because both can be operational decisions. The checkpoint is explicit: Validate portName references in CI. This prevents a console screenshot of one object from being mistaken for the complete effective configuration.

Competing hypotheses: Failure isolation. In the production case, Frontend resolves the short name through its local proxy but receives connection resets after an orders deployment; direct task-IP health checks are green. The healthy observation—Cloud Map namespace, subnet routes, and the application on container port 8080 are healthy.—removes some hypotheses but not all. Competing explanations remain: namespace sharing failed; security groups block the proxy port; portName contract drift prevented proxy configuration; the application itself is down. The discriminating sequence is to describe the active task definition and service deployment, compare portName/discoveryName/clientAlias, inspect proxy logs, then test the task IP and proxy path separately. This ordering favors evidence that separates hypotheses, not a change that merely makes the symptom disappear.

Evidence ladder: Evidence interpretation. The useful evidence bundle is: Short name is accepted locally; direct container port responds; active task definition lacks the service's configured portName; proxy log identifies the mapping failure. What this proves: Namespace and application are healthy while the proxy configuration contract is broken. What this does not prove: A direct task-IP success does not prove SG policy and proxy routing for every client subnet. The next discriminating check is: Compare the running deployment's task-definition portMappings with serviceConnectConfiguration and proxy events. Keep raw timestamps, identifiers, directions, and configuration versions together. Without those fields, observations from different requests can be combined into a compelling but false story.

Bounded repair: Safe remediation. The identified root cause is: The service deployment references a port name no longer present in the task definition, so the injected proxy cannot expose the intended endpoint. The bounded remediation is to restore a matching named port mapping or update Service Connect configuration in the same deployment; add schema validation in CI. This change treats the demonstrated mechanism and preserves rollback. It also respects the boundary that each service belongs to one namespace, and discovery names must be unique there. Avoid bundling unrelated route, policy, DNS, and application changes, because a multi-variable recovery destroys the evidence needed for prevention.

Proof after change: Verification and rollback. Deploy server then client, curl the short name, observe the envoy response path, and confirm proxy connection metrics and logs. Verification must include the previously failing case, a known-good control, forward and return behavior where relevant, and the delayed evidence source if the service exports asynchronously. Deploy server compatibility before clients. Define abort signals before deployment and keep the previous values or templates available. A control-plane success state is necessary but never sufficient when the user-visible outcome is a data-plane transaction.

Production envelope: Scale, security, and operations. Configuration changes require deployments and coexistence during rollout must be considered. The proxy consumes task resources and depends on log/role setup. At scale, small per-resource assumptions accumulate across accounts, Regions, Availability Zones, caches, or state tables. Security review asks who can change the controlling object and which legitimate paths a condition excludes. Operations review asks whether the evidence arrives soon enough for its intended use. Reserve proxy CPU and memory. Test shared namespaces across account boundaries. Together these checks turn a feature into an operable production capability.

Senior-engineer checkpoint: Decision checkpoint. Service discovery success is not proxy-listener or application-path success. Before approving the architecture, require an owner for the feature, a measurable success condition, a failure injection or canary, and a rollback path. Keep a non-Service-Connect access plan for external clients. The lesson is complete only when another engineer can predict the healthy flow, identify the failed layer from evidence, and choose the next check without widening access or changing several independent controls.
